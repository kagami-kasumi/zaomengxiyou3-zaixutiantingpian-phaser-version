# Codex + GPT-5.6 问题总结

## 一、先给结论

面试官问“你平时使用 Codex + GPT-5.6，觉得它有什么缺点”，可能同时在考察三件事：

1. **横向比较能力**：Codex、Claude Code、Cursor、OpenCode 等 Agent 产品，以及不同模型之间有什么取舍。
2. **纵向问题识别能力**：长期使用 Coding Agent 后，是否见过可重复的失败模式。
3. **工程治理能力**：发现失败后，能否定义问题、建立验证闭环，并判断问题来自模型、Agent harness、项目 harness，还是任务本身。

其中最值得展开的是后两项。没有严格 benchmark 时，不应武断地断言某个模型或产品全面优于另一个；但可以根据长期项目实践，准确描述 Coding Agent 的共性失败模式以及自己的治理方法。

“上下文窗口短”已经不适合作为主回答。GPT-5.6 的百万级上下文解决了容量问题，项目中的 [PG-014](../docs/workflow/problems/PG-014-Agent上下文读取路由重复与过量.md) 也证明，曾经的上下文压力有相当一部分来自重复全文读取、错误冷启动路由和无关输出，而不是模型窗口本身。上下文的相关性、状态保持和噪声控制仍是工程问题，但更适合被描述为 **context management**，不宜继续描述成单纯的规格短板。

更好的总回答是：

> Codex + GPT-5.6 的代码生成能力已经很强，我认为当前更主要的问题不是“会不会写”，而是长链路执行的完成度不能被直接信任。Agent 可能在仍有明确未完成项时提前宣告完成，也可能围绕错误理解同时生成实现和测试，形成自洽但不符合原始需求的结果。因此，Coding Agent 的瓶颈正在从 generation capability 转向 execution reliability、completion criteria 和 verification。

## 二、横向问题：可以回答，但不要编造比较结论

横向问题指“Codex + GPT-5.6 相比其他模型或 Coding Agent 产品有什么不足”。这类结论需要在相同仓库、相同任务、相同权限、相同验证标准下做重复实验。没有做过这种 benchmark，就应明确限制结论：

> 我没有对 Codex、Claude Code、Cursor、OpenCode 做过严格的同条件 benchmark，所以不会下“谁全面更强”的结论。我更有把握谈的是自己长期使用 Codex 时观察到的失败模式。

如果面试官继续追问横向取舍，可以谈以下维度，但应当称为 trade-off，而不是未经验证的胜负结论：

- **可定制性与产品耦合**：模型、工具、权限、上下文管理和执行循环通常由 Agent 产品共同决定，闭源产品的默认体验更完整，但可替换性和底层可观测性可能不如自建或开源 harness。
- **执行过程的可观测与可控性**：任务越长，越需要稳定的 trajectory、checkpoint、diff、工具结果和终止原因，否则失败后难以复盘是哪一步出了问题。
- **成本与延迟**：强模型执行简单、确定性的修改可能 overkill；不同任务应按风险和验证收益选择模型与 reasoning effort。
- **可重复性**：Agent 轨迹具有随机性，同一任务可能选择不同文件、不同方案和不同验证深度，调试难度高于确定性程序。

当前不建议再把“上下文只有 272K/376K”作为 Codex 的核心缺点。官方 OpenAI 文档也更强调：给出领域上下文、硬约束和成功标准，在代表性任务上评测，并跟踪长会话中重复 prompt 与工具输出带来的上下文负担，而不是把窗口数字本身当作可靠性的充分条件。参见 [OpenAI Model guidance](https://developers.openai.com/api/docs/guides/latest-model)。

## 三、纵向问题：“偷懒”应当如何定义

“偷懒”只是人的感受，不能作为正式归因，因为模型没有工作积极性或主观懒惰。面试中可主动改口为：

> 我说的“偷懒”不是对模型动机的判断，而是一种可观察的 Agent 行为，更准确地说是 **premature termination（过早终止）** 或 **under-execution（执行不足）**。

一个可操作的定义是：

> 任务存在明确、仍未满足的验收条件；存在权限允许、成本合理且能显著降低不确定性的下一步动作；Agent 却没有执行该动作，并在缺少相应证据时宣告任务完成。

它通常表现为三类行为：

1. **过早终止**：只完成主路径或约 80% 的工作，就输出“已完成”。
2. **隐式缩减范围**：把“更新全部调用方”执行成“更新搜索到的几个调用方”，把“完整系统”执行成“代表性切片”。
3. **验证不足**：存在便宜的 type check、test、lint、全局搜索或浏览器验收，却只凭代码阅读宣布成功。

但不能把所有遗漏都叫“偷懒”。以下情况首先应归入其他问题：

- 需求没有明确成功标准：属于 specification gap。
- 原版事实或业务真值不存在：属于 oracle/evidence gap。
- 单个任务包含多个资料族、多个 owner 和多批验收：属于 workload design 问题。
- 工具权限、网络、依赖或环境不稳定：属于 Agent harness 或 environment 问题。
- 项目规则互相冲突，要求既“轻量窄读”又“每次全文冷启动”：属于 project harness 问题。

因此，“偷懒”只能描述行为症状，不能直接说明根因。

## 四、模型问题还是 harness 问题：不要二选一，按责任层归因

同一次失败通常有多个原因。更有用的方式是区分四层，并寻找**最有能力预防复发的主控制点**。

| 层级 | 典型职责 | 典型失败 | 判断信号 |
| --- | --- | --- | --- |
| 基础模型 | 理解、规划、生成、判断下一步 | 错误理解、局部最优、自我确认、随机遗漏、停止判断不稳 | 在相同 harness 下，某模型显著且稳定地比其他模型更易失败 |
| Agent 产品 harness | 工具调用、权限、上下文/compaction、执行循环、状态和轨迹呈现 | 工具结果丢失、权限受阻、长任务状态衰减、无法复盘、错误终止策略 | 同一模型换 Agent 产品或控制循环后，结果明显变化 |
| 项目 harness | AGENTS、任务拆分、owner、真值、测试、门禁、评审与治理记录 | 范围含糊、局部通过冒充整体完成、重复定义、缺少持久防线 | 加入项目级合同或自动门禁后，多模型的同类复发明显下降 |
| 任务/环境/oracle | 需求、仓库状态、依赖、原版证据、业务裁决 | 需求不可判定、测试只验证错误需求、环境偶发失败 | 人也无法从现有材料得出唯一答案，或失败跟外部状态强相关 |

归因时可以使用一句很重要的话：

> 我不要求给每次失败找一个唯一责任方，而是区分行为症状、主要控制点和残余风险。模型可能产生错误倾向，但如果项目 harness 本可用低成本门禁稳定阻止它，那么工程上的主控制点仍然在 harness。

## 五、本项目给出的真实证据

本项目的问题治理记录显示，很多“看起来像模型偷懒”的现象，实际上是模型倾向与 harness 缺口的叠加。

| 项目问题 | 表面症状 | 更准确的归因 | 治理后得到的认识 |
| --- | --- | --- | --- |
| [PG-005 逆向证据链不完整却宣布闭合](../docs/workflow/problems/PG-005-逆向证据链不完整却宣布闭合.md) | Stage 1-2 漏掉 K 跳跃、误判地面线、无证据设置停点阈值，却曾宣告闭合 | 模型存在局部搜索和过早闭合倾向；更直接的主因是 harness 只要求“找到对应 AS3”，没有共享调用链、SWF 几何、证据分级和双重验证 | 六段证据链、机器真值和负向门禁落地后，同类结论必须留下可复查证据；这不是单靠“换更强模型”解决的 |
| [PG-002 功能条线提前关闭](../docs/workflow/problems/PG-002-功能条线提前关闭.md) | 代表性切片完成被外推成完整系统完成；Stage 1-2 在核心交互仍错误时关闭 | 这是典型 premature success declaration；同时暴露出项目没有“完整系统”的承诺单位和关闭合同 | 功能线、覆盖矩阵、单线 WIP 和用户实测回归把“完成”从语言判断变成证据判断 |
| [PG-007 UI 原生化缺少统一门禁](../docs/workflow/problems/PG-007-UI原生化缺少统一门禁.md) | 真背景、路由可用、零 console error 被误当成原版 UI 已完成，现代覆盖层仍然存在 | 不是模型不会写 UI，而是 verifier 测错了目标；测试证明“能运行”，没有证明“与原版逐状态一致” | 加入显示列表、verified 真值、原版视觉基准、现代例外和逐状态差异证据后，验收目标才与需求一致 |
| [PG-008 Task 缺少可执行规模门禁](../docs/workflow/problems/PG-008-Task缺少可执行规模门禁.md) | 单个 task 同时做逆向、资源派生、实现、运行校准和关闭裁决，执行过长并 compact | 首要问题是 workload design，不应简单归因于模型上下文或偷懒 | 限制 1—2 个工作包、1—2 批验收、默认 0 compact，并在首次 compact 后停止扩张；有界任务的完成稳定性明显提高 |
| [PG-014 Agent 上下文读取路由重复与过量](../docs/workflow/problems/PG-014-Agent上下文读取路由重复与过量.md) | 重复全文读取已注入的 AGENTS，轻量任务也读取战略文档，过早积累上下文 | 项目入口规则冲突和路由不清是主因，不是窗口容量不足 | 任务先分级、注入即视为已读、LSP/rg/窄读分流后，轻量、TS 和正式 task 三类样本均未复发 |
| [PG-004 问题治理缺少效果反馈闭环](../docs/workflow/problems/PG-004-问题治理缺少效果反馈闭环.md) | 提出问题、写出方案后就长期停留在“已治理”，无法证明新代码没有再犯 | 这是治理 harness 缺少持续 eval，不是单次生成质量问题 | 集中审计要求存量清理、增量防复发、反证退回和精确归档；“方案写了”不再等于“问题解决” |

截至 2026-08-24，活跃问题中的 [PG-001](../docs/workflow/problems/PG-001-共享技能规则重复定义.md)、[PG-011](../docs/workflow/problems/PG-011-共享UI组件边界与迁移门禁缺失.md) 和 [PG-013](../docs/workflow/problems/PG-013-关卡运行框架按关卡复制.md) 仍说明一个 Coding Agent 共性：它很擅长在当前文件和当前任务内求局部最优，但如果全局 owner、复用边界和迁移门禁不明确，就容易复制已有规则、页面组件或逐关运行框架。PG-013 已完成 Stage 1-2 怪物 Registry 试点，但其余关卡消费者尚未迁移，不能把试点完成写成问题已关闭。这个倾向可以来自模型，但是否允许它进入代码库并持续扩散，是 harness 和架构治理的问题。

近期 [PG-017](../docs/workflow/problems/PG-017-真值表不管用.md) 又补充了更深一层风险：即使证据链、Schema、测试和现代消费形式上都存在，expected、actual 与实现仍可能共享错误前提。character 657 宠物 HUD 已完成视觉侧首个纠错实例；但猴系又出现“原版合同已有 `attackRange`，现代宠物仍在远处虚空攻击，而专项与 P1R 全绿”的行为反例。这证明问题不只是真值生成是否全面，还包括真值字段是否真的变成运行语义。PG-017 因此已进入 V2 复盘，通用视觉全面性校验器和行为合同运行时 verifier 都尚未完成，不能说问题已经解决。

## 六、如何科学判断责任归属

不能只根据一次失败判断“模型不行”或“harness 不行”。可以设计一个小型因果对照实验：

1. 冻结同一个 commit、任务描述、工具权限、依赖环境和验收标准。
2. 让 Agent 在执行前生成候选 acceptance criteria（验收条件清单），再用独立 oracle（不依赖执行 Agent 自己结论的判定依据，例如原始需求、原版证据或外部运行结果）约束它，避免运行后按结果改标准。
3. 同一模型、同一 harness 重复运行 3—5 次，观察失败是否稳定复现。
4. 保持 harness 不变，只更换模型；再保持模型不变，只更换或加强 harness。
5. 记录需求覆盖率、低成本验证动作利用率、错误完成声明率、返工量、测试/构建结果、token、延迟和人工介入点。

可以按下表解释结果：

| 结果 | 更可能的结论 |
| --- | --- |
| 多个模型都以相同方式失败，增加明确门禁（必须通过，否则不能宣告完成或进入下一阶段的强制检查）后都改善 | project harness 或 specification 是主因 |
| 同一 harness 下，某模型多次稳定失败，其他模型稳定通过 | 基础模型能力或停止策略更可能是主因 |
| 同一模型在不同 Agent 产品中差异明显 | Agent 产品的工具、上下文、权限或执行循环是关键变量 |
| 所有配置都给出不同答案，人也无法从材料判定 | oracle、证据或需求定义不足 |
| 自动测试全过，但用户体验仍错 | 验证目标不完整；不能据此证明模型正确 |
| 同一问题被静态门禁后不再出现，但转移到门禁外的新形态 | harness 有效但覆盖不充分，需要扩充问题定义或进入复盘 |

真正成熟的回答不是“都是模型的锅”或“都是我 prompt 写得不好”，而是能提出可证伪的归因假设。

以上是一套建议的对照实验，不是本项目已经完成的 benchmark。本项目有多次同一 Agent 在门禁补强前后的纵向对照，但没有完成“相同任务、多个模型、重复 3—5 次”的严格横向实验；面试时不能把建议方案说成自己已经做过的实验结果。

## 七、如何建立验证闭环

### 1. 先形成候选验收清单，再让 Agent 开始

可以先让 Agent 把自然语言需求转换成候选验收合同，例如：

```text
[ ] 原始需求中的每个子项都有实现位置
[ ] 全部调用方完成迁移
[ ] type check / lint / unit / integration 按风险执行
[ ] 没有未经授权的范围缩减
[ ] 没有无关文件改动
[ ] 每个“已完成”结论都有命令、diff、截图或真值证据
```

终止条件不应是“代码已经生成”，而应是“验收合同已经有证据地满足”。但如果验收合同也是同一个 Agent 生成的，它仍可能遗漏原始需求，不能因为清单被全部勾选就认为验证已经独立。清单只是组织工具，必须继续锚定用户原始要求、恢复语料、源码/SWF、可执行结果和实际运行反馈。

### 2. 使用多种 oracle，而不是只看测试通过

- 编译器、类型检查和 lint：验证语法、类型和部分静态约束。
- 单元、集成和端到端测试：验证可执行行为。
- 全局搜索和静态门禁：验证遗漏调用方、重复 owner 和禁止回填。
- 机器真值、截图差异和人工试玩：验证视觉、空间、手感和业务语义。
- 原始需求到证据的映射：验证测试没有围绕错误理解自洽。

`test pass` 只能证明被测试的命题成立，不能自动证明原始需求成立。实现和测试若由同一个错误理解生成，完全可能一起通过。

### 3. 用四个机制阻止“实现和测试一起答错”

可以把实现看成考生、测试看成阅卷人。如果答案和评分标准都由考生根据自己的理解现场生成，就可能出现“答错了，但完全符合自己写的评分标准”。本项目把行为验证拆成四个容易解释的机制：

| 机制 | 通俗解释 | 猴系示例 | 它防住什么 |
| --- | --- | --- | --- |
| expected 与 actual 数据流隔离 | **标准答案和考生答卷不能来自同一份草稿。** expected 在实现前从原版 AS3/SWF 和冻结合同得到；actual 从现代游戏真正运行时采集，测试不能调用实现内部 helper 反算答案 | 原版先冻结“攻击距离外追击、进入距离后攻击”；现代运行只上报实际位置、动作和伤害 | 防止实现写错后，测试复制同一个错误常量仍然通过 |
| 合同字段级覆盖 | **不能只点名说‘这道题我看过’，要给每个得分点判分。** 每个合同 id 里的关键字段都要对应场景、运行数据和断言 | 不只检查 41 个合同 id 存在；`attackRange` 必须对应“距离大于它时不能攻击，距离小于等于它时才可攻击”的断言 | 防止 manifest 被 import 了，却没有任何字段真正约束代码 |
| 范围外禁止攻击的负场景 | **不仅证明该做时会做，还要证明不该做时绝不会提前做。** 负场景专门把前置条件设为不满足 | 把怪物放在攻击范围外、1200 索敌范围内：宠物应追击，进入范围前 projectile、hit 和 pet-source damage 都必须为零 | 防止测试只造一个“肯定会命中”的方便场景，漏掉边界和前置条件 |
| 黑盒结构化 trace | **像看比赛录像和计分台，而不是问运动员‘你刚才打中了吗’。** 从系统外记录时间、双方位置、距离、动作、投射物、攻击 id、伤害来源和 HP 前后值 | trace 必须连成“发现目标→距离收敛→进入范围→发起攻击→该宠物来源扣血→清理”，不能只看到特效和最终 HP 下降 | 防止内部自报“已攻击”，也防止玩家、环境伤害或测试传送目标冒充宠物命中 |

四者是一个连续证据链：先用独立 expected 规定原版应当怎样，再把每个字段落实为可执行断言，用负场景卡住动作前置条件，最后从黑盒 trace 证明现代运行真的沿正确过程完成。另一个 AI 可以帮助补测试或审查遗漏，但**换一个 AI 不等于验证独立**；真正的独立来自标准答案、运行数据和实现代码的数据流分离。

还可以再加一层 mutation-kill：故意把 `attackRange`、owner 或命中条件改错，如果测试仍然全绿，就证明 verifier 没有真正覆盖这个字段。它类似故意放一道错题检验阅卷规则是否真的工作。

面试时可简洁表述为：

> 我遇到过原版合同、实现和测试形式上都齐全，但宠物仍在攻击距离外虚空放招的问题。根因不是没写测试，而是测试只确认合同 id 被读取，并用必然命中的 fixture 验证自己。后来我把验证拆成四层：原版 expected 与现代运行 actual 分源、合同字段逐项映射断言、增加“不满足条件不得攻击”的负场景、从系统外采集位置—动作—命中—伤害来源 trace。这样测试验证的是原始行为，而不是实现对自己的解释。

### 4. 区分机器互审和独立事实来源

高风险任务可以让审查 Agent 只读取原始需求、验收标准、diff 和测试结果。它与执行 Agent 的上下文和角色相互隔离，可以降低直接自我确认的概率，但这只是**机器互审**，不是独立 oracle：如果二者使用相同模型、相同机器生成的需求理解和相同错误前提，仍可能共享盲区。

真正更独立的事实来源包括用户原始要求、原版 AS3/SWF、带源哈希的机器真值、编译器结果、外部运行行为和用户实际试玩反证。它们各自只能证明一部分事实，因此仍需组合使用。

### 5. 当前实际参与方式与面试表述

本项目中的 acceptance criteria、治理文档、自动测试和大量 reviewer 结论主要由 Agent 生成或执行。人的参与并不是逐行编写所有标准、逐行 review 全部代码，而主要体现在：提出目标和边界、指出实际体验与声明不符、提供反例、拒绝不充分的“完成”，并推动 Agent 把反复出现的问题固化为门禁和治理记录。

这并不等于“没有参与”，但也不能包装成“我亲自设计了全部 eval，并通过独立人工 review 保证质量”。适度包装应当只是把真实经历整理成工程语言，不能增加没有做过的工作。比较准确的面试说法是：

> 这些验收清单和自动检查大多由 Agent 生成，我不把机器生成的清单或机器互审本身当作独立真值。我的主要作用是给出目标、边界和运行反证，再要求 Agent 把反例沉淀成可执行检查。机器负责大部分实现和机械验证，我保留对需求范围、原版真实性和最终体验的裁决。不过我目前还没有做严格的多模型 benchmark，也没有逐项人工审核全部机器生成的验收标准。

### 6. 把一次修复升级为防复发机制

项目的问题治理流程提供了一个完整闭环：

```text
问题定义
→ 可复查证据
→ 解决方案及边界
→ 测试方案
→ 实际测试结果
→ 关闭标准
→ 后续适用触发与反馈
→ 复发时退回复盘
```

这比单纯要求 Agent “更认真”“多检查几遍”可靠，因为后者无法被执行、测量和回归。

## 八、面试可直接使用的回答

### 30 秒版本

> 我觉得 Codex + GPT-5.6 现在的主要问题不是代码生成能力，而是 Agent 长链路执行的完成度不能直接信任。它有时会完成主路径后提前宣告成功，或者在错误理解上同时生成实现和测试。我口语上会说它“偷懒”，更准确地说是 premature termination 或 under-execution。我的项目里验收清单和多数检查也由 Agent 生成，所以我不会把机器互审当作独立证明；我主要用原始需求、原版证据、可执行结果和实际体验反证来约束它，再把发现的问题固化成门禁。至于是模型还是 harness，目前我没有做严格的横向 benchmark，不会凭一次失败下结论。

### 90 秒版本

> 我长期使用下来，觉得 Codex + GPT-5.6 的核心短板已经不是“不会写代码”，而是 execution reliability。第一，它可能只完成主要路径就 declare success，我把它定义为：仍有明确未满足的验收项，也有低成本、高收益的验证动作，但 Agent 没有执行就终止。第二，Agent 的错误会沿工具循环传播；如果需求 A 被理解成 B，它可能生成 B 的实现和 B 的测试，最后测试全过但需求仍错。第三，长任务中真正困难的也不只是 context window，而是 task 划分、状态相关性和验证证据能否保持。
>
> 我不会把这些全部归咎于模型。我们项目里曾出现漏掉角色跳跃、局部切片冒充完整系统、真背景冒充原生 UI、重复全文读取等问题。后来分别通过证据链、功能线关闭合同、视觉真值和上下文读取路由治理，复发明显下降。这说明模型有局部最优和过早终止倾向，但 harness 决定这些倾向是否进入代码库。这里的验收清单、测试和机器 reviewer 大多也是 Agent 生成的，所以我不把它们本身当作独立真值；我主要提供目标、范围、用户体验反证和最终裁决，让 Agent 把问题沉淀成自动检查。机器负责机械验证，原始需求、原版材料和实际运行结果负责校正机器可能共享的错误前提。

### 被追问“到底是模型问题，还是你的 harness 没做好”

> 我认为这不是一个先验二选一的问题。模型提供概率性的理解、规划和停止判断，harness 提供工具、上下文、任务边界、完成标准和验证反馈。同一行为可能由两者共同产生。我会先描述可观察症状，再找主要控制点：如果多个模型都失败而增加项目门禁后都改善，主要是 harness；如果同一 harness 下某个模型多次稳定失败而其他模型通过，才有更强证据指向模型。工程上更重要的不是替谁免责，而是找到最低成本、最稳定的防复发位置。

### 被追问“既然还需要人校验，为什么还要用 Coding Agent”

> 校验不等于人工重做。大部分机械验证可以由编译器、测试、静态搜索、截图 diff 和审查 Agent 完成；机器互审虽然不是独立真值，仍能减少部分遗漏。人主要提供目标、边界、实际运行反证和最终取舍，而不必重新逐行实现代码。Agent 仍然显著降低实现、搜索、迁移和回归成本，但我不会声称自己人工审核了所有机器生成的验收标准。

## 九、最终提炼

面试时可以记住五句话：

1. **“偷懒”不是动机判断，而是 premature termination / under-execution。**
2. **大上下文解决容量，不自动解决相关性、完成标准和验证可靠性。**
3. **同一个失败可能同时有模型倾向和 harness 缺口，应找主要控制点并做对照实验。**
4. **Coding Agent 当前的核心工程问题，是如何把概率性的生成系统封装成具有稳定 completion criteria、verification loop 和防复发反馈的软件工程系统。**
5. **机器生成的验收清单和机器互审可以提高覆盖率，但不是独立 oracle；面试表达可以结构化，不能虚构人工参与或实验结果。**
