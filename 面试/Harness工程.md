# 面试准备：Harness Engineering 与长期 AI Agent 协作

> 更新基线：2026-08-24。数字和状态来自当前仓库；后续讲述前仍应以代码与台账复核。

## 这份材料怎么用

这份材料专注于可迁移到不同项目的 Harness Engineering、Agent 协作、工程治理和工具集成。游戏逆向与具体系统实现见 [游戏项目.md](游戏项目.md)。

- 30 秒：讲清长期 Agent 协作的问题、方案和结果。
- 2 分钟：展开外部记忆、执行边界、质量反馈和演进方法。
- 深挖：进入上下文工程、Feature Line/Task、治理优先调度、问题治理、自动校验或 MCP/LSP。

表达时不要把 Harness 说成“一组更长的 Prompt”。重点是如何把目标、状态、边界、证据和反馈做成可执行的工程系统。

## 30 秒概述

我在一个长期 TypeScript 遗留系统现代化项目中，设计并持续迭代了一套面向 AI Agent 的协作 Harness。项目跨逆向研究、架构设计、代码实现、视觉验收和文档治理，不同任务可能由不同对话接手，主要风险是上下文丢失、范围失控、状态漂移和误报完成。

我的方案是把项目知识做成按需加载的外部记忆，用 Feature Line 持有完整交付、用 Task 限制单次执行，再增加一个治理优先的全局执行队列，防止紧急工程治理被普通功能任务绕过。结构检查、系统测试、构建和工作流校验形成机器反馈闭环；TypeScript LSP 则补上定义、引用和 diagnostics 等语义导航能力。

一句话总结：**我做的不是让 Agent 记住更多内容，而是让它能按需恢复状态、执行唯一有界工作项，并用机器反馈证明结果。**

---

## 背景与我要解决的问题

单轮代码生成并不难，真正困难的是长期协作：

- 每个新对话都可能从零开始，没有可靠的长期记忆。
- 项目知识分散在代码、任务、历史决策、外部资料和用户反馈中。
- Agent 容易扩大范围、跳过前置研究或顺手重构无关系统。
- 一个小任务完成后，可能被误报成完整功能已经交付。
- 文档、代码、测试和任务状态可能彼此矛盾。
- 上下文不断增长后，Agent 可能因为压缩或切换而丢失关键约束。
- 纯文本搜索难以可靠判断大型 TypeScript 项目中的符号关系。

因此 Harness 需要同时回答五个问题：

1. 新 Agent 应读取什么，而不是把什么都读一遍？
2. 当前唯一允许执行的工作是什么，治理任务是否需要抢占？
3. 做到什么程度才算完成？
4. 如何自动发现越界、不一致和回归？
5. 下一轮如何恢复事实、决策和剩余工作？

## 核心模型

```text
入口与上下文路由
        │
        ▼
分层外部记忆
目标 ── 当前状态 ── 历史 ── 证据 ── 统一语言
        │
        ▼
执行边界与调度
全局治理队列 ── Feature Line ── Task
        │
        ▼
实现与反馈
代码/文档变更 ── 结构检查 ── 测试 ── 构建 ── 状态回写
        │
        └──────── 发现系统性问题时进入问题治理
```

这套设计有七个原则：

1. **入口是地图，不是百科全书**：入口只保留高频硬规则和阅读路由。
2. **上下文按任务加载**：轻量请求、正式实现、评审、逆向和治理读取不同资料。
3. **交付承诺与工作单元分开**：Task 完成不自动等于完整功能完成。
4. **事实、推断和设计选择分开**：Agent 不能把证据缺口补写成确定结论。
5. **规则同时需要前置约束和后置反馈**：自然语言负责引导，脚本和测试负责纠偏。
6. **约束边界，不微管理实现**：明确目标、禁止范围和验收方式，把实现空间留给 Agent。
7. **调度优先级必须结构化**：只在说明里写“先治理”不够，抢占关系必须进入唯一执行队列和自动校验。

## 六个关键设计

### 1. 分层外部记忆：解决跨对话失忆

#### 问题

如果所有背景都塞进一个入口文件，冷启动成本会持续增长，内容也会快速过期；如果完全依赖聊天历史，新对话又无法恢复状态。

#### 方案

我把信息按职责拆开：

| 信息层 | 回答的问题 |
| --- | --- |
| 战略导航 | 项目目标、阶段路线和基本原则是什么 |
| 交付台账 | 当前完整承诺、状态和关闭条件是什么 |
| 全局执行队列 | 是否有工程治理项需要先于游戏功能执行 |
| Task 看板与独立合同 | 当前最小工作单元、依赖、验收和上下文预算是什么 |
| 历史记录 | 过去完成了什么，为什么这样决策 |
| 证据索引 | 某个结论是否已经研究清楚、是否完成实现 |
| 架构与统一语言 | 代码边界和推荐命名是什么 |
| 工作流协议 | 不同类型任务如何执行、验证和收尾 |

入口文件不复制这些内容，只负责路由：

- 轻量问题只读入口和直接相关文件。
- 正式执行先读全局队列；没有可执行治理项时，才读取当前 Feature Line、Task、证据和架构资料。
- 评审与问题治理加载各自协议。
- 历史文件只在追溯决策或修改已完成工作时读取。

#### 价值

这相当于建立了一个可查询的项目记忆，而不是要求 Agent 一次性记住整个仓库。上下文体积可控，文档职责也更容易验证。

### 2. Feature Line / Task：解决范围失控和误报完成

两个持久层级回答不同问题：

```text
Feature Line：对用户或业务的完整交付承诺
  └─ Task：一次执行只处理的最小可独立验收工作包
```

- **Feature Line** 持有完整范围、关闭矩阵和最终证据。
- **Task** 包含输入、产物、完成定义、验收批次、禁止范围、拆分触发和状态更新。
- **`/goal`** 只是“执行唯一全局工作项”的命令，不再是另一个需要同步的持久实体。

项目保持单条 Feature Line `WIP=1`。Task 完成后仍在同一条线上激活下一个 Task，只有完整关闭合同满足后才切换系统。每个新 Task 默认预计 0 次上下文压缩；第一次 compact 被视为规模超限信号，只允许结束当前检查、回写安全检查点并拆分剩余工作。

这个模型避免了两种常见问题：

- 完成一个局部 Task 就宣称整个功能完成。
- 一次对话不断追加工作，最终超出可验证和可交接的范围。

### 3. 治理优先全局队列：解决“知道要先治理，却还是先做功能”

早期协议虽然写了问题治理优先，但游戏看板仍然是默认入口。真实执行中，Agent 会看到一个游戏 `Ready` Task 后直接开始实现，说明自然语言优先级没有变成结构化调度。

我增加了一个很薄的全局执行队列：

```text
/goal
  → 先检查治理队列
      ├─ 有 Ready/Blocked：只处理该 PG 治理项，完成后立即停止
      └─ 队列为空：回退到唯一 Active Feature Line 的唯一 Ready Task
```

队列最多允许一个可执行治理项，治理完成后同一次执行不能顺手进入游戏 Task。校验器同时覆盖治理抢占、空队列回退、多 owner 和非法状态等正反样例。这个机制后来通过真实抢占与真实回退样本验收，并把对应问题归档。

### 4. 证据合同：解决 Agent 在资料不足时边猜边写

对于遗留系统、外部规范、复杂业务规则或视觉复现，找到相关文件不等于结论已经成立。

我要求关键结论至少记录：

- 一手来源和实际调用链；
- 输入、状态、触发条件、边界和可观察结果；
- 已确认事实、推断、未知和现代设计选择；
- 现代实现由哪个 owner 消费；
- 自动验证和运行验证分别证明什么；
- 哪些反证会让结论重新进入调查。

这套方法不只适用于游戏逆向，也可以迁移到：

- 遗留业务系统迁移；
- 第三方 API 行为兼容；
- 数据口径和报表重构；
- 复杂权限与审批流程；
- 设计系统和交互还原。

关键思想是：**先把来源材料转成与架构无关的行为合同，再决定现代实现。**

### 5. 前置约束 + 后置反馈：解决“规范写了但没人遵守”

前置约束负责告诉 Agent 应该做什么：

- 必读资料与按需阅读路由；
- 当前治理执行项，或当前 Feature Line 与 Task；
- 可写范围和禁止范围；
- 完成定义与验证命令；
- 何时必须停止扩展并交接。

后置反馈负责发现偏差：

- 工作流校验检查文档、引用和状态是否一致；
- 结构检查阻止继续向热点文件堆逻辑；
- 专项测试验证确定性业务规则；
- 类型检查和构建验证完整工程；
- 运行时验收验证无法由静态测试证明的行为；
- 搜索或审计确认旧定义、重复数据源和废弃路径已经消失。

核心原则是：**能够机械判断的规则，应尽量变成脚本、测试、Schema 或构建失败。**

### 6. 问题治理：解决系统性缺口被当成零散建议

普通评审很容易留下“建议抽象”“职责有点重”“测试不够”之类无法关闭的意见。

我把会持续伤害系统演进能力的问题升级为治理对象，例如：

- 跨文件重复；
- 模块耦合和边界漂移；
- 单一数据源缺失；
- 生命周期规则不统一；
- 测试盲区；
- 文档、任务和代码状态分裂。

每个治理对象必须包含：

| 部分 | 必须回答的问题 |
| --- | --- |
| 问题定义 | 为什么它是系统性问题 |
| 证据 | 哪些文件、调用链、重复或事故能证明 |
| 解决方案 | 治理到什么边界，明确不做什么 |
| 测试方案 | 如何证明方案有效 |
| 测试结果 | 实际执行结果和剩余风险 |
| 关闭标准 | 什么情况下才允许关闭 |
| 效果反馈 | 后续任务是否复发，方案是否需要退回 |

评审负责发现和分级，问题治理负责让系统性问题可确认、可执行、可验证、可关闭。活跃问题会在代码、架构、Task 或工作流改动收尾时扫描触发条件；归档问题不再常驻消耗上下文，只在门禁失败、用户反馈复发或新设计推翻旧决策时按 ID 重开。方案不充分时保留旧版本进入复盘，而不是覆盖历史。

## 自动校验与质量门禁

当前验证链按风险分层：

| 改动类型 | 主要验证 |
| --- | --- |
| 工作流、任务或领域文档 | 工作流与引用一致性校验 |
| 在现有源码中新增逻辑 | 修改前先运行结构检查 |
| 业务系统实现 | 专项测试 + 全量系统测试 |
| 类型和打包边界 | TypeScript 检查 + 生产构建 |
| 跨层混合改动 | 完整门禁 |
| 视觉、交互或时序 | 自动检查 + 运行时观察 |

工作流校验脚本已从早期的基础文件检查演进到 1500 余行，覆盖：

- 必读文件和必要命令是否存在；
- 全局治理队列是否正确抢占，空队列是否回退游戏任务；
- Feature Line 与 Task 是否保持唯一激活/Ready 状态；
- Task 详情与看板是否双向一致；
- Task 是否包含有界工作包、验收批次、拆分触发和 compact 预算；
- 已完成工作是否迁移到历史；
- 稳定 ID 和跨文档引用是否真实存在；
- 前置证据是否满足实现条件；
- 工作流变更是否有治理记录；
- 统一语言是否出现重复推荐名或禁止别名；
- 问题治理是否完成触发条件和效果反馈扫描。

最重要的不是校验规则数量，而是把“文档是否可信、状态是否可执行”从人工印象变成可重复结果。

## MCP + LSP：从文本搜索升级到语义导航

文本搜索适合快速发现候选，但不知道某个命中是符号引用、同名变量、注释还是字符串；面对路径别名、barrel export 和 re-export，仅靠关键词容易漏改或误改。

因此我给 Codex 接入了基于 MCP 的 TypeScript LSP：

```text
Codex（MCP Host）
  → codex-lsp（MCP Server）
  → typescript-language-server（LSP Server）
  → TypeScript 项目与 tsconfig
```

- MCP 负责把外部能力暴露为可发现、带 Schema 的工具。
- LSP 负责 diagnostics、definition、references、symbols 和 rename 等语言语义。
- 构建与测试继续负责全项目类型和运行行为，LSP 不替代它们。

实际验证分为四层：

1. MCP 初始化成功。
2. 工具能够被 Host 发现。
3. 下游语言服务器能够启动。
4. 真实项目上的 diagnostics、定义和引用查询有效。

工程集成中还处理了 GitHub ZIP 不包含 submodule，以及 Windows 下无 shell `spawn` 不能稳定执行 npm `.cmd` 包装器的问题，最终改为直接启动 `node.exe + typescript-language-server/lib/cli.mjs`。

这部分不是从零实现 MCP 或 LSP 协议。我的工作是识别纯文本理解的风险、选择并集成现有组件、解决 Windows 启动链问题，并证明端到端语义调用有效。

分层使用方式是：

```text
文本搜索：发现候选位置
LSP：确认符号关系与类型诊断
编译和测试：验证完整工程与行为
```

## 这套 Harness 如何演进

它不是一次性设计完成的，而是从真实失败中逐步增加约束：

1. **入口从百科全书变成路由**：固定必读清单导致上下文浪费，后来按任务类型加载。
2. **活跃状态与历史分离**：完成记录移入历史，活跃看板只保留当前执行信息。
3. **Task 与完整交付分离**：Task 完成曾被误解为系统完成，因此增加 Feature Line 关闭合同。
4. **移除重复 Goal 实体**：`/goal` 收敛为执行命令，Feature Line 持有长期承诺，Task 持有单次执行边界，减少状态同步面。
5. **把 compact 变成规模反馈**：新 Task 默认 0 次 compact，第一次压缩后停止扩张并拆分，而不是继续依赖摘要工作。
6. **增加治理优先全局队列**：真实执行曾绕过治理说明，因此用结构化队列和门禁实现抢占与回退。
7. **从文档规则升级为自动门禁**：引用、状态、前置依赖、任务规模和命名进入校验脚本。
8. **从评审建议升级为问题治理**：系统性问题必须有证据、方案、测试、反馈、复盘和归档机制。
9. **逆向从“找到文件”升级为证据链**：局部资料必须追到共享调用链、行为合同和验证。
10. **代码理解从 grep 扩展到 LSP**：文本候选之后用语义工具确认影响范围。

最大的体会是：**高价值规则通常来自具体事故，应该沉淀成路由、数据边界、测试或校验，而不是继续把 Prompt 写长。**

## 对其他场景的适配

这套方法不是游戏专用。可复用的是“外部记忆、执行边界、证据合同和反馈闭环”，需要替换的是领域索引与验收方式。

| 场景 | 保留的 Harness | 需要替换的领域部分 |
| --- | --- | --- |
| 遗留系统迁移 | 分层记忆、证据合同、Feature Line/Task、回归门禁 | 旧接口、数据库行为、兼容矩阵 |
| 企业业务平台 | Feature Line、统一语言、问题治理、权限边界 | 业务流程、角色、审计和合规规则 |
| 数据工程 | 数据源证据、单一口径、依赖门禁、回归测试 | Schema、血缘、质量指标和重跑策略 |
| SDK/API 集成 | 调用链、未知分级、端到端验证 | 版本矩阵、错误码、限流和兼容性 |
| 设计系统/UI 重构 | 资产索引、状态矩阵、视觉验收 | 组件、Token、响应式和无障碍规则 |
| 内容或知识库项目 | 上下文路由、来源分级、状态回写 | 引用、版权、事实更新和发布流程 |

迁移时可以保留四个最小部件：

1. 一个只做路由的入口。
2. 一个完整交付台账、一个当前工作台账，必要时再加治理抢占队列。
3. 一套证据与完成定义。
4. 一条能够自动结束的验证链。

小型短期项目不需要复制完整体系。可以只保留路由入口、一个当前 Task 和一条测试命令；随着真实失败出现再增加功能线、治理或历史机制。

## 结果与可量化事实

- 建立了 Feature Line、Task、治理队列、证据索引和历史记录分层，并移除了重复的持久 Goal 状态。
- 全项目保持单条交付线 `WIP=1`，Task 完成不再自动代表系统完成。
- 工作流校验脚本已超过 1900 行，并与资源/数据校验、关卡架构检查、结构检查、系统测试和构建组成门禁。
- 当前案例仓库包含 167 个 `src/systems` 模块、95 个测试文件和 102 个 `test/check/audit` 脚本入口，可用于检验 Harness 是否能支撑长期演进。
- 通过 MCP 接入 TypeScript LSP，增加 diagnostics、定义、引用、符号和安全重命名能力。
- 系统性问题从零散评审意见升级为带证据、验证、关闭标准和效果反馈的治理对象。
- 已用真实执行样本证明治理 Ready 能抢占游戏 Ready、治理结束会停止、空队列会恢复唯一游戏 Task。
- 新 Agent 不依赖口头交接，可以按入口路由恢复目标、依赖、边界、状态和下一步。

真正重要的结果是三点：

- **可恢复**：新对话能从落盘状态继续。
- **可约束**：Agent 可以自主行动，但范围和权限明确。
- **可验证**：完成结论有机器反馈和可复查证据。

---

## 不应过度声称的部分

- Harness 降低错误概率，但不能保证 Agent 永远正确。
- 文档驱动不代表文档天然可信，仍需代码事实和自动一致性校验。
- 自动测试不能替代产品判断、真实用户反馈和无法自动化的运行验收。
- MCP/LSP 是现有组件的工程集成，不应包装成自研协议实现。
- `WIP=1` 适合当前强依赖、长期接力的项目；多条真正独立的交付线可以采用受控并行。
- 专业化 Agent 或 Subagent 是可选实现手段，不是 Harness 成立的前提。
- 小项目应保留核心思想并删减流程，而不是整套照搬。

---

## 2 分钟表达示例

我做过一套比较完整的 Harness Engineering 实践。背景是一个长期 TypeScript 遗留系统现代化项目，工作跨研究、架构、实现、评审和文档治理，而且不同对话会由不同 Agent 接手。真正的问题不是单次生成代码，而是新 Agent 会失忆、任务容易越界、局部完成容易被误报成整体完成，文档和代码状态也会逐渐漂移。

我的方案分四层。第一层是外部记忆，把目标、当前交付、历史、证据和统一语言拆成职责独立的文档；入口只做路由，按任务类型加载最小上下文。第二层是执行边界，用 Feature Line 表示完整业务承诺，用 Task 表示一次执行的最小可验收单元，`/goal` 只是执行唯一工作项的命令。治理任务通过独立全局队列抢占普通功能工作，新 Task 默认不允许依赖上下文压缩完成。第三层是证据合同，把确认事实、推断、未知和现代设计选择分开，避免资料不足时边猜边写。第四层是反馈，把调度、引用一致性、任务规模、结构边界、系统测试、类型检查和构建做成自动门禁。

我还建立了问题治理闭环，让跨文件重复、边界漂移和数据源分裂不再停留在 Code Review 建议，而是必须有证据、方案、测试、关闭标准和后续效果反馈。在代码理解方面，我通过 MCP 接入 TypeScript LSP，让 Agent 在文本搜索之后用定义、引用和 diagnostics 确认影响范围，再由编译和测试验证行为。

这套 Harness 已经在 167 个系统模块、95 个测试文件的真实仓库里持续演进。我的核心经验是：不要试图用更长的 Prompt 管住 Agent，而要把项目状态外部化、把执行范围和优先级数据化，并让可以判断的规则进入机器反馈。

## 常见追问

### Q：这和写一份很详细的 AGENTS.md 有什么区别？

详细 Prompt 仍然是自然语言建议，而且会随着项目增长变得昂贵和过时。Harness 把状态、任务、证据和历史拆成可查询的数据，并通过脚本、测试和构建反馈。入口只负责告诉 Agent 在当前场景该读取什么。

### Q：为什么不用 Jira、Linear 或 GitHub Issues？

这些工具擅长团队协作和业务追踪，但 Agent 仍需要仓库内可版本化、可全文搜索、能与代码一起审查的执行上下文。两者并不冲突：外部工具可以管理组织级计划，仓库内 Harness 负责让 Agent 获得精确、可执行的局部状态。

### Q：为什么现在只保留 Feature Line 和 Task，不再维护 Goal 实体？

Feature Line 已经负责完整业务承诺，Task 负责一次执行的范围、验收和上下文预算。过去再维护一层 Goal 会产生重复状态和同步成本，所以现在把 `/goal` 收敛为“执行唯一全局工作项”的命令。两层持久状态已经足够区分整体承诺和局部完成。

### Q：为什么需要单独的全局执行队列？

因为“治理优先”如果只写在文档里，Agent 仍可能从游戏看板直接拿一个 Ready Task。全局队列把抢占关系变成唯一调度入口：有治理项就只做治理，队列为空才回退游戏任务，而且这些规则有正反校验和真实运行样本。

### Q：为什么要限制单条 Feature Line WIP=1？

当前案例中的任务共享大量状态和验证链。WIP=1 可以减少跨线切换、半成品和文档竞争。它不是绝对原则；如果交付线数据、代码和验收真正独立，可以并行，但应明确所有权和合并边界。

### Q：文档维护成本不会很高吗？

会，所以文档必须职责正交、按需加载，并把一致性转成脚本。活跃状态与历史分开，避免入口不断膨胀。判断标准不是“文档越多越好”，而是它是否减少了重复调查、错误实现和交接损耗。

### Q：如何防止文档和代码事实不一致？

第一，把可检查的关系变成稳定 ID、Schema 和校验脚本；第二，完成任务时要求状态回写；第三，关键结论仍以代码、测试和运行结果为准；第四，历史只负责追溯，不反向覆盖当前事实。

### Q：问题治理和普通重构有什么区别？

普通重构可以是局部改善。问题治理针对会持续伤害演进能力的结构性缺口，必须先证明问题，再定义边界、方案、测试和关闭标准，并在后续任务中观察是否复发。

### Q：为什么把第一次 compact 当成任务过大的信号？

压缩可以帮助继续对话，但摘要不能代替精确源码、证据和合同。对于高证据密度任务，第一次 compact 说明工作包已经超过原来的可验证边界；此时结束检查、保存安全状态并拆分，比凭摘要继续扩张更容易审查和交接。

### Q：为什么需要 MCP，直接让 Agent 执行命令不行吗？

命令适合过程调用，但 Agent 还需要发现能力、理解结构化参数和返回结果，并区分只读与修改操作。MCP 提供标准工具边界；具体语义能力仍由下游服务提供。

### Q：有了 LSP，为什么还要文本搜索、typecheck 和测试？

它们回答的问题不同。文本搜索发现候选，LSP 确认定义、引用和诊断，typecheck 验证全项目类型，测试验证业务行为。任何一层都不能单独证明功能正确。

### Q：MCP/LSP 是你自己实现的吗？

不是。我集成了现有的 `codex-lsp`、`lsp-tools-mcp` 和 TypeScript language server，解决插件注册、submodule 和 Windows 进程启动问题，并完成端到端验证。工程价值在于正确选型、集成、排障和证明有效。

### Q：专业化 Agent 是不是必须的？

不是。专业化 Agent 适合研究、实现、评审或治理之间上下文和权限明显不同的场景。Harness 的核心是状态、边界和反馈；是否拆 Agent 取决于任务独立性，而不是为了多 Agent 而多 Agent。

### Q：如何把这套方法迁移到另一个项目？

先识别四件事：完整交付单位、最小工作单元、权威证据源和自动验证链。再建立一个路由入口、一个当前状态台账和一个完成合同。不要先复制所有文档，等真实失败出现后再增加历史、治理或专业化工具。

### Q：如果从项目第一天就使用 Codex，最开始应该怎么和它说？

我不会第一句话就让 Codex 写完整项目，也不会一开始照搬一套很重的流程。第一步是把它当作新加入项目的工程师，先给清楚业务目标、用户、技术与权限边界、权威资料，以及“什么结果才算成功”；然后让它先检查当前仓库和工具环境，复述理解、列出未知项，并和我一起建立最小可执行闭环：一个简洁的 `AGENTS.md` 作为入口、一个当前 Task、一套可自动结束的检查命令，以及第一个可运行、可验收的纵向切片。

接下来让 Codex 按“读取上下文 → 提出小计划 → 实现 → 运行检查 → 展示证据 → 回写状态”的循环推进，而不是一次生成整个系统。项目发展中出现跨对话失忆、范围失控、同类缺陷复发或任务过大时，再分别增加外部记忆、任务拆分、自动门禁和治理机制。也就是说，项目初期最重要的不是写一条万能 Prompt，而是先建立目标、边界、事实来源和反馈闭环，再让 Harness 随真实问题演进。

实际启动时，我会给 Codex 类似这样的指令：

> 你是这个项目的协作开发者。项目要为【目标用户】解决【核心问题】，第一阶段成功标准是【可观察结果】。技术栈和不可突破的边界是【约束】，需求与设计的权威来源是【资料位置】。先不要实现完整功能；请先检查仓库和可用命令，复述你对目标、现状、风险和未知项的理解，然后提出一个能独立运行和验收的最小纵向切片，以及对应的完成标准和自动检查。经确认后，只实现这个切片，验证通过后再总结证据与下一步。

面试时可以压缩成一句话：**先让 Codex 建立项目模型和验证闭环，再让它写第一个可验收切片；流程不是一次设计完的，而是从真实失败中逐步固化。**

### Q：最大的教训是什么？

高价值规则通常来自具体事故。最有效的沉淀方式不是继续增加 Prompt，而是把事故转成更清晰的数据所有权、更小的执行边界、可查询的证据，或者一条会失败的自动检查。
