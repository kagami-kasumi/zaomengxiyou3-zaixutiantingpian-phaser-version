# 炼丹炉四功能规则完整性审计

本文是 `TASK-SETTINGS-169` 的交付物。范围只审计强化、合成、分解、打造的业务规则、现代映射、双 owner 与 V6 往返；不修改事务代码，不补造完整装备数值，也不重复 167/168A/168B 已闭合的显示列表与视觉真值。

## 审计结论

- 四功能的共同 owner、暂存/返还、灵魂消费、随机注入、原子拒绝和成功后 V6 保存链路已经存在；专项测试均通过。
- 强化的概率/降级/保护、分解的品质产物、打造的 78 本可达制作书和 Fusion 的 112 条现代配方事务均有确定性覆盖。
- 当前不能宣称“四功能全量完成”。阻塞项是：164 件装备的权威基础数值/强化成长/职业与品质门禁尚未形成可消费全集；Fusion 原版 9 条时装时戳配方未进入现代注册表；打造灵珠类小数属性仍以 AS3 小数直接写入现代百分数点字段；全装备就绪后的四事务全量重放尚未执行。
- 原版按中文角色名反查 owner、无容量预检、部分静默失败和空引用不作为现代目标；现代显式 `PlayerSlot`、安全反馈、容量原子拒绝和提交后即时保存均保留为已记录的现代设计选择。

状态语义：`闭合` 表示原版合同、现代映射和确定性测试一致；`全装备依赖` 表示规则已知但无法对 164 件装备全集验收；`缺失` 表示原版可达路径未进入现代事务；`现代差异` 表示有意的安全/离线设计；`未知` 表示当前证据不能完成裁决。

## 缺口分层与关闭标准

### 现有目录内可闭合

- 打造三类小数属性统一换算为现代百分数点，并为旧 V6 已制作实例给出兼容/迁移裁决。
- Fusion 9 条原版时装配方必须二选一：实现原版时间语义，或取得用户批准后以永久时装作为显式现代例外；不得继续从“112 条通过”推出全量。
- 在不改变事务 owner 的前提下补四功能联合静态矩阵：系统规则、正式 host 提交、即时保存和重载后的库存/灵魂/实例一致。

这些都是后续“四功能事务收口”范围，本 task 只登记，不修改代码。

### 依赖完整装备数据

- 164 件装备的 `fillName/showId/name/type/user/quality/slot`、基础 12 属性、强化成长、实例/堆叠语义和原始字段单位必须形成有 locator、反证条件与 schema 的权威全集。
- 全集必须与 431 入包身份目录一对一关联；不能建立第二个 inventory identity registry。
- 以全集重放：强化准入/成长、分解品质/类型/角色、Fusion 属性继承、打造静态产物与宝石叠加。

### 独立实现/迁移

- 全装备数据与 UI 分成证据冻结、现代数据/页面接入两个阶段；UI 必须继承对应原版显示列表、verified 真值和逐状态差异门禁。
- 百分数单位修正、Fusion 时装语义和所有 V6 兼容属于全装备就绪后的四事务收口；若需要 V7，必须由存档扩展阶段统一拥有 schema，不在单个事务内私建版本。

## 后续有界输入

1. `TASK-SETTINGS-170A` 只冻结 1.1 全可穿戴装备权威数据，不修改现代事务或 UI。
2. 后续 UI 证据 task 冻结所有装备在背包/穿戴页的显示列表、真图标/角色穿戴资源、动态字段和门禁。

4. 最后执行四事务收口，处理本审计的百分数单位、9 条时装配方、全量重放和存档兼容。
