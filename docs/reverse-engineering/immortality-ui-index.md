## 六段证据链

### 1. 可观察问题

需要回答：页面有哪些静态和动态对象；按钮各状态和命中区怎样；P1/P2 如何切换；25 个丹药格如何解锁；服用、炼制和失败分支按什么顺序改变灵魂、背包与加成；哪些字段进存档，以及原版何时真正落盘。

### 2. 源证据

- 行为主证据：
  - `scripts/export/immortality/ImmortalityInterface.as`
  - `scripts/export/immortality/SingleImmortality.as`
  - `scripts/export/immortality/ExchangeImmortality.as`
- 共享交叉证据：

- 只读派生物：`local-resources/regima/task-outputs/task-settings-066-map-services/deep-immortality/`。恢复源和 legacy extraction 原始结果均未修改。

### 3. 调用链与 owner

`MapMenu` 创建 character 990；`ImmortalityInterface.added()` 按当前玩家创建职业选择器，点击后以角色中文名找到 `User`，刷新灵魂、加成与 25 格状态。两人局按 P2、P1 顺序添加，却依次派发 P1、P2 点击，最终默认选中 P2；单人局默认 P1。选择器只有帧 1 normal、帧 2 selected，没有独立 hover/pressed 帧。

原版以角色中文名反查 owner，重复职业会碰撞。这是原版事实；现代实现必须以稳定玩家槽位保存 owner，属于避免串档的现代等价设计，不把碰撞行为伪装成需求。

### 4. 状态与事务

25 格按五列品阶、五行类型排列。每行只允许服用“连续已服用前缀后的第一个未服用品阶”，且背包必须已有该丹药；后阶即使已有物品也保持锁定。已服用格在运行时叠加对应丹药图，下一格的服用按钮按条件显示。

服用要求所选玩家灵魂不少于 1000。失败只提示“灵魂不足1000！”。成功顺序是扣 1000 灵魂、隐藏按钮、写入 5×5 标志、移除一个丹药、刷新页面并派发 `RefreshPill`；原版不在此处主动保存。

炼制弹窗对每一阶检查两种材料，再检查 `djlist` 容量。材料不足提示“道具不足”，容量满提示“背包空间不足”，均不改变数据。容量检查发生在消耗材料和尝试堆叠成品之前，因此满列表即使本次会释放格子也拒绝。成功时先移除两种材料，再加入对应丹药，最后派发 `RefreshPill`。5% “走火”仅把成功提示换成“走火了，丹药可能变质了！”，产物仍是同一正确丹药。

弹窗派发刷新后，根页没有监听该事件，故新炼成丹药不会立刻令服用按钮出现；切换 owner、成功服用或重开页面后才刷新。这是已确认的原版可见特性，未来若修正须作为经批准的现代例外。

### 5. 存档往返

`User.getSaveObj()` 写入 `lhValue`、`immortalitylist` 和背包字符串；`User.setSaveObj()` 恢复灵魂与 5×5 标志，旧存档缺字段时默认全零。`MemoryClass.setStorage()` 收集双方玩家，`saveGame()` 才写入槽位。服用和炼制本身不调用保存，只有之后的显式保存使变更持久。

当前现代 V6 已有每名玩家的灵魂与背包，但没有丹药 5×5 标志。`TASK-SLICE-155A` 应给玩家存档增加可选、校验后的 5×5 二值字段，缺失时迁移为全零，复用现有六槽 `localStorage`。事务成功后立即调用既有活动槽保存，是现代可靠性选择，需标注为不同于原版显式保存时机。

### 6. 现代实现合同

- 复用原版可见资源、坐标、按钮态、P1/P2 selected 帧、余额和炼制弹窗，不允许整页现代可见层替代。
- owner 以玩家槽位为权威；灵魂、背包、丹药标志均在同一玩家事务中更新，失败分支必须原子不变。
- 默认保留原版“炼制后根页不即时刷新服用按钮”的表现；若产品决定修正，必须登记为现代视觉/交互例外。
- 实现后须在 940×590 对 normal、hover、pressed、selected、P1/P2、余额、五种拒绝/成功路径和关闭返回逐状态截图，并与本文派生基准并排或叠图。
