# 怪物与关卡组织中的设计模式

本文是一份面试讲稿，说明三个问题：为什么 Codex 没有一开始就采用更好的设计模式、怪物与关卡后来如何重新划分职责，以及这些设计和常见面向对象模式有什么关系。

设计模式不是必须套用的代码模板，而是对常见职责关系和变化方式的总结。项目真正追求的是清晰的数据所有权、较低的修改成本和可验证的扩展边界，而不是使用更多模式名称。

## 1. 为什么 Codex 没有主动采用设计模式

不能简单回答“Codex 不在乎设计模式”。更准确的原因是：**当任务只明确要求尽快交付可玩切片时，可运行、可通关和测试通过是显式目标，长期架构质量却是隐性目标。Codex 会优先完成更容易观察和验收的部分。**

### 1.1 它优先优化任务中写明的目标

如果任务是“让这个关卡可以通关”，最明确的完成信号是角色能移动、怪物能生成、战斗能结算。至于以后还会增加多少关卡、多少怪物，以及哪些规则必须复用，如果没有写进任务合同，Codex 很可能选择当前改动最小的实现路径。

因此问题不是它完全不会架构设计，而是当时的任务把“可玩切片”设成了显式奖励，却没有把“跨关卡复用”和“未来扩展成本”设成验收条件。

### 1.2 设计模式依赖未来变化方向

是否应该抽象，取决于未来什么地方会变化。例如：

- 新怪物主要变化的是数值、移动方式、自动决策，还是攻击技能？
- 同一种怪物会不会出现在多个关卡？
- 这是一次性复刻，还是后续仍会不断扩展？
- 当前是否值得承担迁移旧代码的成本？

这些产品路线和成本判断通常由人类掌握。Codex 可以比较方案，但不能只靠当前几个文件推断出项目未来最重要的变化轴。

### 1.3 它通常只读取当前任务需要的局部上下文

实现一个关卡时，Codex 可能只需要读取当前关卡、直接依赖和测试。要发现“多个关卡正在复制同一套怪物运行规则”，则需要跨文件比较多个消费者并理解后续路线。

如果每次小功能都扫描整个仓库并主动全局重构，不仅成本很高，也会违反任务范围。因此局部执行边界本身是合理的，只是大型模块应该在编码前显式加入架构分析阶段。

### 1.4 过早使用设计模式也可能是错误

两段代码相似，不代表它们一定应该共享父类或抽象。它们可能只是暂时相似，之后会向不同方向发展；也可能为了保留原版差异而必须分开。

如果要求 Codex 无条件“多用设计模式”，它也可能制造万能父类、过深继承或没有实际需求的复杂框架。好的架构不是模式越多越好，而是在有足够变化样本后建立合适边界。

### 1.5 人类应提出架构目标，不必指定模式答案

人类不需要直接命令“这里使用策略模式”。更好的要求是：

> 这个模块以后会持续增加怪物和关卡，不接受规则继续按关卡复制。请先分析状态由谁负责、哪些地方会变化、有哪些候选架构，再开始实现。

接下来可以让 Codex 负责扫描重复、提出方案、比较组合与继承、设计迁移边界并实现验证。人类主要提供长期目标、优先级和可接受成本。

## 2. 为什么怪物与关卡需要重构

当前工程已经具备若干正确边界：

- `Stage*Layout` 保存关卡平台、停点、刷怪点、机关和传送门等内容数据。
- `Stage*FlowSystem` 管理波次、同屏上限、Boss（关卡头目）、失败和通关。这里的 Flow 指关卡流程编排模块。
- `Stage1CombatSystem` 实际被多个正式关卡复用，提供怪物数值、索敌、接近、攻击阶段和伤害结算。
- `MonsterPhysicsSystem`、`MonsterDefeatRewardSystem` 和 `DropSystem` 已分别拥有怪物物理、死亡奖励和掉落规则。
- 怪物视觉系统与 Phaser bridge（连接纯业务规则与 Phaser 显示对象的适配层）已能跨相邻关卡复用部分怪物素材和动作。

但当前结构仍有四个扩展风险：

1. **通用能力带有关卡名称。** `Stage1CombatSystem` 已经是跨关卡 owner（唯一负责某类状态和规则的模块），却仍以首个切片命名，导致“通用规则”和“关卡适配”在语义上混杂。
2. **同一怪物存在两个运行时登记点。** 部分关卡 Flow 保存 `aliveEnemies`，场景 bridge 又保存带战斗、物理和视图的怪物 `Map`（按键快速查询数据的字典结构），必须靠人工同步创建、死亡和移除。
3. **特殊怪物重复实现共同算法。** `Monster3System` 与 `Monster30System` 分别拥有最近目标选择、状态转换和攻击决策；继续按怪物复制会增加修复和校准成本。这里的 AI 指怪物自动选择目标、移动和攻击的决策逻辑。
4. **内容差异与行为差异没有稳定接缝。** 数值、物理类型、AI、技能、动画集和掉落表需要组合，但目前部分由通用表拥有、部分由专属系统拥有、部分在关卡 bridge 中连接。

重构目标不是“让类更漂亮”，而是建立唯一的数据与生命周期 owner，使以下变化可以局部完成：

- 同一种怪物出现在不同关卡时，只复用怪物定义和行为，不复制实现。
- 多种地面近战怪共用索敌、接近和攻击决策，只替换数值、动作和技能。
- 飞行、远程、施法和 Boss 可以替换行为策略，而不扩张出深层继承树。
- 关卡只决定何时、何地、生成什么，以及何时算遭遇完成；不实现怪物内部战斗规则。
- Phaser 视图只消费怪物状态并播放视觉，不成为战斗事实来源。

## 3. 推荐的职责边界

### 3.1 关卡拥有遭遇，不拥有怪物内部规则

关卡应拥有：

- 地形、平台、障碍、机关和出口；
- 出生点、波次、生成延迟和同屏上限；
- 停点、封路、Boss 触发和通关条件；
- 本次遭遇关联的怪物稳定 ID 或存活计数。

关卡不应拥有：

- 怪物如何选择玩家；
- 怪物如何接近、攻击、受击和死亡；
- 怪物基础数值、状态抗性和技能内部算法；
- 动画帧推进、命中结算和掉落随机算法。

“关卡只负责怪物列表”仍然过窄。准确说法应是：**关卡负责遭遇编排，怪物系统负责怪物运行。**

### 3.2 怪物静态定义与运行状态分离

推荐区分：

```ts
type MonsterDefinition = Readonly<{
  monsterTypeId: string;
  statsProfileId: string;
  physicsProfileId: string;
  brainId: string;
  abilitySetId: string;
  animationSetId: string;
  rewardProfileId: string;
  lootTableId: string;
}>;

type MonsterRuntime = {
  id: string;
  monsterTypeId: string;
  x: number;
  y: number;
  hp: number;
  state: string;
  targetId?: string;
};
```

`MonsterDefinition` 是可复用内容配置；`MonsterRuntime`（运行时对象）是一只具体怪物在本局中的可变状态。关卡出生点只引用 `monsterTypeId`（怪物类型的稳定标识），由怪物工厂完成定义解析与运行时创建。

### 3.3 唯一运行时注册表

`MonsterRuntimeRegistry`（怪物运行时注册表，集中登记当前存活怪物）应成为存活怪物的唯一登记点，第一版只需要：

- 稳定 ID；
- 创建、查询和安全移除；
- 按怪物类型或遭遇 ID 查询；
- 幂等死亡/移除；
- 向关卡 Flow 返回生命周期结果。

关卡 Flow 可以保存遭遇 ID（稳定标识）、生成计划、已生成数量和已击败数量，但不再复制完整怪物状态。第一版不引入完整 ECS（把实体拆成数据组件，再由系统批量处理的架构）、全局事件总线（向全项目广播事件的中介）或依赖注入容器（集中创建并提供模块依赖的工具）。

### 3.4 行为使用组合，而不是深继承

推荐把共同 AI 表达成策略，即把可替换的决策算法独立出来：

```ts
type MonsterBrainId =
  | 'ground-melee'
  | 'ground-ranged'
  | 'flying-melee'
  | 'flying-ranged'
  | 'stationary-caster'
  | 'scripted-boss';
```

地面近战策略可统一完成：

1. 从合法存活目标中选取目标；
2. 判断警戒范围；
3. 面向目标；
4. 未进入攻击距离时移动；
5. 进入距离后进入攻击状态机；
6. 攻击结束后回到追踪状态。

怪物之间的差异由参数和能力集合表达。Boss 的阶段脚本可以是独立策略，但仍复用目标选择、伤害、物理、状态效果和死亡结算。

### 3.5 动画和掉落不由怪物对象直接执行

怪物运行状态只表达 `approach/windup/active/recovery/hurt/dead`，即接近、攻击前摇、攻击生效、攻击后摇、受击和死亡等事实。动画系统根据状态和 `animationSetId` 选择素材、帧和播放规则；Phaser bridge 负责显示对象。

同理，怪物定义只引用 `lootTableId` 和 `rewardProfileId`。死亡奖励系统负责随机、生成、归属和拾取，不应让每个怪物子类自行创建掉落物。

## 4. 与面向对象理念的贴合度

### 4.1 封装

封装不是“把字段放进 class（类）并设为 private（只允许类内部直接访问）”，而是让规则有明确 owner：

- 目标选择规则属于目标选择/AI owner；
- 重力和落地属于怪物物理 owner；
- 伤害与命中去重属于战斗 owner；
- 波次与通关属于关卡 Flow；
- 动画播放属于视觉 owner。

调用者只依赖公开合同，不直接修改另一个系统的内部状态。

### 4.2 抽象

抽象应来自稳定变化轴，而不是为了减少文件数：

- 所有怪物都有稳定 ID、类型、位置、生命和生命周期，这是稳定抽象。
- “地面近战”“飞行远程”是可复用行为族，可以抽成策略。
- Monster16 的具体六种攻击不是所有怪物共同能力，不应塞进基础怪物抽象。

### 4.3 多态

Java 常用接口实例实现多态；TypeScript 中也可以用判别联合（根据一个标记字段区分不同数据形态）、函数表或满足同一接口的纯函数（相同输入总得到相同输出，且不偷偷修改外部状态）实现：

```ts
type MonsterBrain = {
  update(context: MonsterBrainContext): MonsterBrainResult;
};
```

多态的价值是调用方只知道 `brain.update()`，而不是要求所有实现必须继承同一个有状态父类。

### 4.4 继承与里氏替换

所有怪物在领域上都可以称为 `Monster`，但不代表每个怪物都应该继承一个包含 AI、动画、掉落和物理的巨大 `Monster` 基类。

如果父类假设“怪物受重力、沿 X 轴接近、只有一个攻击窗口”，飞行怪、固定炮台和多阶段 Boss 会不断覆盖父类方法，最终违反里氏替换原则：调用方无法再把任意子类当作具有一致语义的父类使用。

因此现代实现只保留最小共同合同，差异通过组合获得。继承可以用于非常稳定、确实满足替换关系的局部视图适配，但不作为怪物玩法主架构。

### 4.5 SOLID 对应关系

SOLID 是五条常见面向对象设计原则的缩写，重点不是背字母，而是控制职责、扩展方式和依赖方向：

- **SRP 单一职责：** 一个模块只承担一种主要变化原因。Flow 编排遭遇，Brain（怪物决策模块）负责决策，Physics 负责移动，Combat 负责结算，Visual 负责播放，Reward 负责奖励。
- **OCP 开闭原则：** 新功能尽量通过增加定义或策略扩展，而不是反复修改稳定的公共代码。新增怪物通常不需要修改每个关卡和通用调度循环。
- **LSP 里氏替换：** 任何实现都应遵守共同合同，调用方替换实现后不应出现语义意外。所有 Brain 使用相同输入和输出，不依赖脆弱的父类默认行为。
- **ISP 接口隔离：** 不强迫模块依赖自己用不到的能力。飞行怪不必实现地面落地接口，无掉落单位不必伪造掉落逻辑。
- **DIP 依赖倒置：** 上层流程依赖抽象合同，不直接依赖底层框架对象或某个具体类。Flow 依赖“生成怪物、收到死亡结果”的合同，而不依赖 Phaser Sprite（Phaser 的画面对象）或具体 `Monster16` 类。

## 5. 与 Java 传统设计模式的联系

| 经典模式 | 本项目中的对应 | 适用理由 | 注意事项 |
| --- | --- | --- | --- |
| Strategy 策略（把可替换算法单独封装） | `MonsterBrain`、目标选择、移动和攻击选择策略 | 同一运行时可以替换地面近战、飞行远程或 Boss 决策 | 不要把每个数值差异都变成一个策略类 |
| State 状态（用明确状态及转换描述对象生命周期） | 接近、前摇、生效、后摇、受击和死亡状态机 | 明确动作转换、不可重入窗口和死亡生命周期 | 简单状态可用联合类型与纯函数，不必为每个状态创建 class（类） |
| Factory Method / Abstract Factory 工厂（集中处理对象创建） | 根据 `monsterTypeId` 创建定义、运行状态、物理与视觉适配 | 隔离关卡出生数据和具体构造细节 | 工厂不应同时承担更新、查询和销毁 |
| Registry 注册表（按稳定标识集中登记和查询对象） | `MonsterDefinitionCatalog`、`MonsterRuntimeRegistry` | 提供定义查找和唯一运行时 owner | 静态定义目录与可变运行时注册表必须分开 |
| Adapter 适配器（转换两个不同接口） | `Stage*GameplayBridge`、怪物视觉 bridge | 把 Phaser 对象转换为系统快照和命令 | Adapter 中不得重新实现领域规则 |
| Facade 外观（给复杂子系统提供少量统一入口） | 对场景暴露少量怪物运行时调度入口 | 降低场景对多个底层系统的直接耦合 | Facade 只编排，不囤积规则和状态 |
| Observer / Domain Event 观察者/领域事件（事实发生后通知多个响应者） | 怪物生成、受击、死亡、移除结果 | 让 Flow、奖励和视觉响应同一生命周期事实 | 第一版优先显式返回事件数组，不急于引入全局事件总线 |
| Template Method 模板方法（父类固定流程，子类覆盖部分步骤） | 传统 `BaseMonster.update()` 的固定流程 | 可作为理解共同生命周期的启发 | 在 TypeScript 中优先组合纯函数，避免父类 hook（预留覆盖点）不断膨胀 |
| Flyweight 享元（多个实例共享不可变的公共数据） | 多只同类型怪物共享只读 `MonsterDefinition` 和动画元数据 | 避免每个实例复制静态表 | 运行时 HP（生命值）、目标和状态绝不能共享 |
| Command 命令（把“要执行的动作”表示成独立数据） | AI 输出移动、开始攻击、释放技能等意图 | 决策与执行分离，便于确定性测试 | 不必为每条命令创建 Java 式类层级 |

这些模式是对变化关系的命名，不是代码生成模板。Java 中常以接口、抽象类和对象实例表达；TypeScript 项目可以用类型、只读配置、函数映射和纯函数获得相同解耦效果。

## 6. 不采用的方向

### 6.1 不建立万能 `BaseMonster`

禁止把数值、AI、物理、动画、掉落、状态效果和 Phaser Sprite 全部塞入一个父类。它会形成 God Object（知道并负责过多事情的“万能对象”），迫使特殊怪物覆盖大量不适用行为。

### 6.2 不一次性引入完整 ECS

项目目前需要的是唯一稳定 ID 和生命周期登记，还没有证据表明必须引入完整 ECS。只有实体数量、跨系统查询或性能问题确实需要时，才值得承担这套架构的复杂度。

### 6.3 不为“复用”抹平原版差异

共同策略必须允许参数化警戒距离、二维/横向距离、攻击窗口、技能选择和移动方式。不能为了共用一段代码，把飞行怪、Boss 或原版特殊动作强制改成普通地面怪行为。

### 6.4 不让关卡 Flow 成为实体仓库

Flow 需要知道遭遇进度，但不需要持有战斗、物理、动画和掉落的完整副本。通关判断应读取注册表或明确的生命周期结果。

## 7. 面试时怎么回答

如果面试官问“这些拆类操作 Codex 完成不是很简单吗，为什么还需要人类提出”，可以这样回答：

> 拆类本身对 Codex 并不难，难的是判断什么时候值得拆、应该沿哪个变化方向拆，以及是否值得承担迁移成本。当时任务的显式目标是尽快完成可玩切片，所以 Codex 优先优化可运行和可验收结果；跨关卡复用和未来怪物扩展没有进入完成合同。另一方面，我也不希望 Agent 看到重复就擅自做全局抽象，因为过早抽象同样会产生万能基类和错误边界。
>
> 后来的改进不是每次由人类指定某个设计模式，而是在大型模块开始前先明确状态所有权、未来变化轴、候选方案和验证方式，再让 Codex 完成方案比较、拆分和实现。人类负责长期目标和取舍，Codex负责分析与执行。设计模式只是这个过程可能得到的结果，不是目的。

可以再用一句话收束：**Codex 会优先完成显式目标；如果长期架构也是目标，就必须把它写进任务边界、讨论流程和验收标准。**
