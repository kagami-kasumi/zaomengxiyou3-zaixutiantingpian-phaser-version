## 结论摘要

总体结构已有明确的任务合同、证据链、唯一执行项、治理分流和归档机制，未发现必须阻塞游戏开发的 High 问题。主要改进方向是减少同一规则和状态的手工副本、分离 harness 与游戏专项检查、降低恢复与收尾成本。以下区分已确认问题与尚未验证收益的设计建议。

## 主要问题

### Medium：规则存在多个手工副本，已出现语义偏差

AGENTS.md:13 允许 warning 文件中的轻量小修在说明理由后局部修改；CLAUDE.md:84 则要求 warning/error 都先拆分，agent-protocol.md:82 又使用“应先拆分”。同一任务可能因客户端入口不同而触发不同工作范围。入口、README 与详细协议还重复维护调度和读取路线。

建议：每项规则指定一个权威位置；客户端入口只保留真正必须常驻的硬约束与链接。必须重复的摘要由同源数据生成或做等价校验。验收应覆盖“warning + 轻量小修”等决策样例，而不仅是关键词存在。

### Medium：当前调度区混入历史状态

task-board.md:7 声明唯一 Ready 为 214，但 :13 在同一个“当前推荐”章节保留“唯一 Ready 仍为 211”。execution-queue.md:17 在空队列下保留过去生成 208A 的完成叙述，而 :21 声明本文件不持有游戏 task id。日期可解释历史，但执行入口仍要求 agent 自行辨认新旧。

建议：当前推荐只保留一个当前快照与必要阻塞；历史事件放入历史记录或链接。第一步可直接清理旧快照；后续再考虑从权威 task 元数据生成推荐、看板和当前指针。功能线范围、机制事实、切片证据仍保留各自职责，不合并为一个万能表。

验收：所有当前入口返回同一执行项；历史事件不会被读取为当前指令；完成归档后旧合同仍可定位。

### Medium：harness 检查入口绑定游戏专项检查

package.json:183 的 check:workflow 同时执行 workflow、PG 合同、资源标注和关卡架构检查。因此单纯协作规则维护也会进入资源与游戏架构门禁。本次命令还输出 src 中领域别名 warning，说明命令边界比名称宽。

建议：增加独立 check:harness 入口，仅验证路由、链接、调度状态和治理合同；保留 check:workflow 的兼容性，再逐步明确它作为组合命令的定位。全量检查继续包含资源与游戏专项，避免拆分后漏验。

验收：harness 文档任务可独立检查；混合任务与全量检查仍覆盖原有门禁。此次未审阅校验器内部实现，不断言当前内部完全可分离。

### Low：compact 的恢复指令不够统一

AGENTS.md:75 要求首次 compact 后只完成检查、回写与拆分；:107 又要求上下文过长时优先 compact 并复查，agent-protocol.md:66 的收尾选项也保留“优先 compact”。前者有明确停止边界，后两处容易让人误解成恢复正常执行。

建议：保留现有规模限制，明确区分“同一 task 继续执行”和“compact 后安全交接”。把后者收敛为固定检查点：当前合同、已完成产物、未完成项、运行中检查、下一允许动作。是否放宽 compact 门禁需要独立证据，本次不建议直接取消。
