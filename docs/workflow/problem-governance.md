# 问题治理协议

本文规定系统性工程问题如何被定义、确认、治理、关闭、出清和必要时复盘换案。它属于 AI 协作脚手架，不记录具体游戏复现任务。每个已登记问题必须拆到 `docs/workflow/problems/` 下的独立文档；本文件只维护通用协议、活跃索引、归档索引和模板。问题治理不在“提出方案”时结束，也不允许已经证明稳定的问题无限留在每次扫描集合中。

## 适用范围

使用本协议的场景：

- 评审发现跨文件重复、模块耦合、边界漂移、测试盲区、数据源分裂或生命周期规则不统一。
- 用户或 reviewer 明确提出“这是一个问题”，需要人和 AI 共同确认后再治理。
- 一个局部 bug 暴露出更深层的系统性缺口，例如桥接层承载领域规则、共享数据表复制到多个系统。
- 代码质量门禁或评审协议发现的风险需要被拆成可验证的治理对象。

不使用本协议的场景：

- typo、注释、单个常量、单文件局部 bug 或无需协商的小修。
- 已有明确游戏 task 的正常实现流程。
- 单纯玩法逆向事实摘录，除非该事实暴露现代代码的系统性问题。

## 问题定义

本项目中的“问题”不是任意代码瑕疵，而是会持续伤害系统演进能力的结构性缺口。一个问题通常具备以下至少两项特征：

- 影响多个文件、多个角色、多个系统或多条调用路径。
- 修改一个业务事实需要同步改多处代码。
- 不同模块对同一规则的表达不一致。
- 当前实现能跑，但继续扩展会显著增加维护成本。
- 测试只能证明局部行为，不能覆盖真实集成路径。
- 问题背后存在职责边界、数据归属、生命周期或验证策略不清。

局部拼写、单个资产 key 或一个边界断言缺失可以直接修；只有暴露出系统性缺口时才升级为问题治理。

## 治理记录结构

每个问题治理文档必须包含 7 部分：

1. **问题定义**：问题本体、系统性影响和不治理的后果。
2. **证据**：文件、行号、重复次数、结构 warning、测试缺口或调用链。
3. **解决方案**：准备怎么改、改到什么边界、明确不做什么。
4. **测试方案**：证明方案正确所需的系统测试、构建、搜索、人工验收或评审复查。
5. **测试结果**：实际运行结果、剩余 warning、风险和未覆盖点。
6. **关闭标准**：完整关闭、部分缓解和需要沉淀为门禁的条件。
7. **适用触发与反馈记录**：声明哪些文件、概念、任务或工作流事件会触发复核，并持续记录通过、复发、方案不充分或不适用样本；如果换过方案，还要保留方案版本与复盘结论。

问题文档还必须在开头写明稳定 `PG-*` id、状态和来源。一个问题只占一个文档；不在总协议中继续堆叠问题正文。归档只改变索引与扫描责任，不删除原证据、失败尝试或历史反馈。

## 状态机

问题使用下列语义状态；独立文档可在同一阶段后附加更细的说明，但不得改变阶段语义：

- `待确认` / `待治理`：已有问题候选或已确认，尚未执行方案。
- `治理中`：正在处理存量缺口，关闭证据未齐。
- `效果观察中`：存量治理已落地，正收集关闭标准要求的增量样本。
- `复盘中`：出现复发、方案不充分或关键假设被推翻，暂停沿用原方案，正在重新定义根因与选案。
- `已关闭待归档`：关闭标准已满足，但尚需补齐出清证据或观察型方案的关闭后样本。
- `已归档`：已满足出清门禁，从常规适用性扫描集合移除。

状态可根据事实跨阶段前进，但从“效果观察中”开始任何 `复发` 或 `方案不充分` 都必须转为 `复盘中`，不能只追加一次局部补丁后继续保持原状态。

## 治理流程

1. **提出问题**：先写清问题定义和证据。
2. **共同确认**：涉及架构边界、系统拆分或较大范围改动时，由用户确认是否值得治理。
3. **建立文档**：在 `docs/workflow/problems/` 新建一个独立 `PG-*` 文档，并加入下方索引。
4. **选择落点**：游戏复现工作进入 `docs/tasks/`；协作协议、校验脚本和评审规则进入 `docs/workflow/`。
5. **执行治理**：保持范围收敛，一次只处理一个清晰问题或一个可验收子问题。
6. **验证关闭**：按测试方案运行检查；证据不足时不能宣称关闭。
7. **沉淀规则**：同类问题可能复发时，把关闭标准转为质量门禁、评审规则或自动校验。
8. **持续反馈**：后续变更命中问题触发条件时，回写效果样本；复发时立即退回治理，不得继续保持“观察中”或“已关闭”。
9. **关闭出清**：按出清门禁补齐关闭摘要和重开信号，将索引项转入归档索引，不再参与日常扫描。

## 关闭出清与归档

“已关闭”不应成为无限期常驻的扫描状态。一个问题同时满足以下条件时必须出清：

1. 独立文档中的关闭标准全部满足，没有未解释反证。
2. 测试结果中有可定位的关闭证据，而不是只有“已修复”结论。
3. 已留下至少一种持久防复发手段：自动测试/静态门禁、唯一 owner 合同或可执行评审规则。
4. 依赖增量效果的观察型方案，已取得关闭标准要求的后续适用样本；硬门禁已完整证明的问题不强制额外等待时间。
5. 文档写明关闭摘要、持久防线、归档日期和精确重开信号。

出清操作：

1. 将独立文档状态改为 `已归档`，在文档开头增加“归档信息”。
2. 从“活跃问题索引”移除，加入“问题归档索引”；原 `PG-*` id 和原文档路径不变。
3. 后续常规收尾只读活跃索引，不读归档问题的触发条件，也不为其写“不适用”样本。
4. 归档索引是追溯地图，不是第二个待扫描清单。

归档问题只在以下硬信号出现时按 ID 定向唤回：用户/reviewer 明确报告同类复发；其持久门禁或回归测试失败；新设计明确要推翻其 owner/边界决策；或变更直接引用该 `PG-*` id。唤回时将其重新加入活跃索引，状态设为 `复盘中`，归档索引保留原归档事件作为历史。

## 复盘与方案更换

当样本结论为 `复发` 或 `方案不充分`，不得默认“原方案加一个补丁”。同一 `PG-*` 进入如下复盘流程：

1. **冻结结论**：状态转为 `复盘中`，原方案标记为方案 V1/V2 等历史尝试，不覆写。
2. **重建事实**：区分是执行漏项、测试盲区、根因判断错误，还是方案边界本身不成立。
3. **评估选项**：至少记录“继续补强”与“替换方案”两类选项的成本、风险、迁移和验证差异；边界或大范围发生变化时再由用户确认。
4. **建立新版本**：在原问题文档追加方案 V2/V3，明确保留、废弃和迁移项，同步更新测试方案与关闭标准。
5. **重新验证**：新方案必须重新证明存量清理和增量防复发；原方案的成功样本不能替代新版本证据。

复盘记录至少包含：触发样本、原假设、失败类型、保留项、废弃项、候选方案、选择理由、新验证合同。只有根因和系统边界明显变成另一个问题时才新建 `PG-*`；否则沿用原 ID，保持可追溯性。

## 效果反馈闭环

所有代码、架构、任务体系或工作流变更在收尾前执行一次**问题适用性扫描**：

1. 只读取“活跃问题索引”，审查待治理、治理中、效果观察中、复盘中和已关闭待归档问题；不遍历“问题归档索引”。
2. 用各 `PG-*` 的触发条件判定当前 diff 是否适用；不得仅凭任务名称或“测试通过”跳过。
3. 对适用问题运行其指定的窄搜索、系统测试、覆盖差异或评审，在问题文档中记录样本。
4. 样本结论只能是 `通过`、`复发`、`方案不充分` 或 `不适用`。`不适用` 用于主动审计解释为何一批新代码没有产生有效样本，无需为每个无关小修造日志噪音。
5. `复发` 或 `方案不充分` 必须更新测试结果，转入“复盘中”并建立方案新版本；已归档问题按硬信号定向重开。
6. 长期无适用样本时，必须判断是近期确实没有命中、问题定义过窄，还是关闭标准不可执行；不得无限期无证据观察。
7. 任务交接给出简短的“问题治理反馈”：命中的 `PG-*`、样本结论和回写位置；如无命中，说明已扫描且无适用问题。

效果评估必须同时覆盖：

- **存量解决程度**：原始证据中的旧问题还剩多少。
- **增量防复发效果**：后续适用任务是否遵守方案、是否出现新的同类问题。

## 与其他协议的关系

- `review-protocol.md` 负责发现和排序问题；本协议负责把系统性发现变成可治理、可关闭的对象。
- `code-quality-gates.md` 负责硬性质量门禁；问题治理可以把反复出现的问题沉淀成新门禁。
- `docs/tasks/execution-queue.md` 负责让需要抢占游戏工作的活跃 PG 进入 `/goal` 调度；PG 合同和状态事实仍以本协议及独立问题文档为准。
- `task-generation.md` 负责生成游戏任务；属于游戏复现或现代实现的缺口才进入任务看板。
- `governance-log.md` 记录脚手架规则变化；问题治理协议和问题文档结构的变化必须写入治理日志。

## 模板

```md
# PG-000 问题名称

状态：待确认。

来源：问题来源。

## 1. 问题定义

问题本体、系统性影响和不治理的后果。

## 2. 证据

- 可复查证据。

## 3. 解决方案

方案、边界和明确不做的事项。

## 4. 测试方案

- 自动检查、搜索验证或人工验收。

## 5. 测试结果

当前结果和后续样本。

## 6. 关闭标准

- 完整关闭条件。
- 只能算部分缓解的情况。

## 7. 适用触发与反馈记录

触发条件：

- 命中问题的文件路径、领域概念、任务类型或工作流事件。

- 存量剩余缺口检查。
- 增量新代码防复发检查。

方案版本/复盘记录（只在换案时启用）：

| 版本 | 触发样本 | 失败类型 | 保留/废弃 | 候选与选择理由 | 新验证合同 |
```
