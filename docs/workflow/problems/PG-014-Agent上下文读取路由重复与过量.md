# PG-014 Agent 上下文读取路由重复与过量

状态：已归档。

来源：2026-08-01 用户观察到 Codex 多次使用 `Get-Content`，并进一步确认重复全文读取和无条件冷启动资料会占用主对话上下文；用户审阅整改清单后要求进入问题治理并优先排期。

## 1. 问题定义

当前工作流已经规定 UTF-8、`rg` 定位和片段读取，但冷启动入口仍同时要求每个新对话读取 `AGENTS.md` 与 `TASK_OUTLINE.md`，轻量请求规则又要求只读直接相关文件。支持 `AGENTS.md` 自动注入的 Codex 仍可能按文案再次通过 shell 全文读取同一文件，轻量请求也可能无条件加载与当前问题无关的项目战略导航。

这不是单次命令偏好，而是跨客户端、跨任务类型持续存在的上下文路由缺口：

- 同一份项目规则可能被客户端注入一次、shell 再读取一次。
- 轻量请求与正式游戏 task 使用同一冷启动资料集，任务分级没有真正控制首批上下文。
- 现有规则强调读取方式，却没有明确“相关输出量、重复输出和聚合全文”才是治理对象，容易把命令次数误当优化指标。
- TypeScript 定义、引用和符号定位没有写明 LSP 优先、`rg` 降级的路径，Agent 可能逐文件探索调用关系。
- 多个入口文件重复声明“每次对话读取 `TASK_OUTLINE.md`”，单点修正容易再次漂移。

不治理会让轻量请求和长任务都更早积累无关输出，增加 compact、关键信息被噪音淹没和重复探索的概率；同时也可能诱导出“少调用命令但一次输出更多”的错误优化。

## 2. 证据

- `AGENTS.md:25-28` 要求新对话默认先读 `AGENTS.md`、`TASK_OUTLINE.md`，但 `AGENTS.md:38` 又规定轻量请求只读直接相关文件，冷启动顺序存在冲突。
- `TASK_OUTLINE.md:5-8` 要求新的 AI 默认读取 `TASK_OUTLINE.md` 自身，没有按任务类型限制。
- `CLAUDE.md:20` 将 `TASK_OUTLINE.md` 标为“每次对话”必读；`README.md:64-66` 同时保留无条件双入口和轻量窄读两种表述。
- `docs/workflow/README.md` 的冷启动路由仍写“新对话默认只读 `AGENTS.md`、`TASK_OUTLINE.md`”，说明冲突已跨多个入口复制。
- `tools/validate-workflow.mjs` 校验 UTF-8 和片段读取纪律，但没有拒绝轻量请求无条件读取 `TASK_OUTLINE.md`，也没有防止已注入 `AGENTS.md` 被再次全文读取。
- 2026-08-01 当前对话已复现：`AGENTS.md` 内容已作为项目指令进入上下文后，Agent 仍按“默认先读”执行了显式全文读取，并同时全文读取 `TASK_OUTLINE.md`；这证明现有文案会真实触发重复上下文，而非仅为理论风险。
- 首次登记只把 PG-014 放到问题索引最前，游戏 `task-board.md` 仍首先展示当时的唯一 Ready task；用户复核后指出这没有表达真实执行优先级，证明“问题优先”与“执行队列优先”需要同时可见。

## 3. 解决方案

本问题作为当前脚手架优先治理项，按一个有界工作包执行以下整改：

1. 修正冷启动顺序：先使用当前已生效的项目指令判定任务类型，再按分流读取资料；支持自动注入时把 `AGENTS.md` 视为已读，不再通过 shell 全文读取。
2. 将 `TASK_OUTLINE.md` 改为正式游戏 task、`/goal`、任务生成/重排和项目路线判断时按需读取；轻量请求、局部评审、局部排错和脚手架局部讨论默认不读。
3. 在 `AGENTS.md`、`README.md`、`CLAUDE.md`、`TASK_OUTLINE.md`、`docs/workflow/README.md`、`document-map.md` 与 `agent-protocol.md` 同步同一语义，避免客户端入口漂移。
4. 明确治理指标是无关输出、重复输出和聚合全文，而不是 `Get-Content` 调用次数；禁止为减少次数而在一次命令中合并多个大型文件全文。
5. 增加重复读取判断：文件未修改且已读取时不重复全文读取；compact 后关键合同复核、精确实现证据和文件已变化时允许重新窄读。
6. TypeScript 定位在 LSP 可用时优先使用 symbols/definitions/references/diagnostics，LSP 不可用或结果不足时降级为 `rg`；定位能力不能代替修改前读取精确实现。
7. 扩展 `tools/validate-workflow.mjs`，拒绝轻量请求无条件读取 `TASK_OUTLINE.md`、`CLAUDE.md` 将其标为“每次对话”等回归，并保留现有 UTF-8、乱码停止和片段读取门禁。
8. 改造后用轻量请求、TypeScript 局部任务、正式逆向/游戏 task 三类真实样本进入效果观察；依据是否重复全文读取、是否误读战略文档、是否准确命中权威资料和是否发生 compact 评估效果。

明确不做：

- 不新增 `TASK-DOCS-*` 或把脚手架治理塞入游戏 `task-board.md`。
- 不以减少命令数量为目标，不禁止必要的 `Get-Content -Encoding UTF8`。
- 不在第一阶段引入全仓库 embedding、SQLite AST 索引、自建代码搜索 MCP 或自动加载的大型 repository map。
- 不让摘要、LSP 或目录地图替代修改源码前的精确实现读取，也不降低逆向六段证据链要求。

## 4. 测试方案

- 更新 `tools/validate-workflow.mjs` 并运行 `node --check tools/validate-workflow.mjs`、`npm run check:workflow`。
- 增加负向样例，确认以下回归会失败：轻量请求要求读取 `TASK_OUTLINE.md`；`CLAUDE.md` 将其标为“每次对话”；入口要求已注入 `AGENTS.md` 仍显式全文读取。
- 用 `rg` 检查各入口不再保留互相冲突的“每次对话双入口”表述，同时继续保留正式 task 的权威路线。
- 执行一个轻量请求样本：不 shell 全文读取已注入的 `AGENTS.md`，不读取 `TASK_OUTLINE.md`。
- 执行一个 TypeScript 局部任务样本：LSP 可用时先定位，随后只读取目标实现和必要消费者；LSP 不可用时记录 `rg` 降级。
- 执行一个正式逆向或游戏 task 样本：仍完整遵守当前 task、证据链、资源路由和关键合同复核，证明减噪没有削弱正确性。
- 三类样本记录读取范围、重复全文次数、compact 情况和是否出现错误推断；不能只统计命令次数。

## 5. 测试结果

- 存量入口已统一：`AGENTS.md`、`CLAUDE.md`、`TASK_OUTLINE.md`、根 `README.md`、工作流 README、文档地图和执行协议均改为“先分类、注入即已读、战略导航按需读取”。
- 读取纪律已明确为控制无关输出、重复输出和多个大型全文聚合；文件未变化不重复全文读取，compact/证据复核时允许重新窄读；TypeScript 使用 LSP 优先、`rg` 降级并保留精确源码阅读。
- `tools/validate-workflow.mjs` 已加入五个负向样例，覆盖注入后重复读取、`TASK_OUTLINE.md` 每次对话、轻量路由、聚合全文和 LSP 规则回归。
- 轻量真实样本：只用 `rg -n -F -e 'check:workflow' package.json` 命中脚本入口，未读取 `AGENTS.md`、`TASK_OUTLINE.md` 或其他战略资料。
- TypeScript 局部真实样本：LSP document symbols 定位 `InputBindings`，references 精确返回定义与第 102/103 行两个消费者，diagnostics 为零 error；随后只读取 `InputSystem.ts` 第 48—109 行，未逐文件探索。
- 正式 `/goal` 路由真实样本：用窄查确认唯一 Active 线、唯一 Ready `TASK-SETTINGS-069B`，只读取其定义开头核对类型、功能线、目标和规模预算；没有再次全文读取已读入口。整改前发生的一次多文件全文聚合作为反向基线保留，整改后样本未复发。
- 三类样本均未发生 compact，也未产生由减读导致的错误推断。

## 6. 关闭标准

- 支持自动注入的 Codex 不再因项目规则要求而 shell 全文重读 `AGENTS.md`。
- 轻量请求默认不读取 `TASK_OUTLINE.md`；正式游戏 task 和路线工作仍能稳定读取正确入口。
- 所有入口文档对冷启动和按需读取的表述一致，自动校验能够拒绝已知回归。
- 大型文档继续先定位后读取片段，且没有出现为了减少命令数而聚合多个大型全文的替代问题。
- TypeScript 局部任务在 LSP 可用时优先定位、不可用时可靠降级，不因少读而错过必要消费者。
- 轻量、TypeScript、正式逆向/游戏三类真实样本均通过，未发生由过度减读导致的错误推断。

只修改一处入口、只删除 `Get-Content` 示例、只减少命令次数、只通过一次工作流校验，或尚未取得三类真实样本，都只能算部分缓解。
