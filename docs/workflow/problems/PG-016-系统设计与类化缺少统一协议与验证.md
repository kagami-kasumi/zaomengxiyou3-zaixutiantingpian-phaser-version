# PG-016 系统设计与类化缺少统一协议与验证

状态：待治理（方案待后续对话讨论）。

来源：2026-08-19 用户把此前的关卡类化与本次宠物类化并列，明确提出“系统设计也应该作为一个系统”，需要规划一份教模型如何开展初步系统设计的文档，同时指出类化与系统设计本身缺少可执行的验证方法。

## 1. 问题定义

项目已有任务、逆向、代码边界、评审和问题治理协议，但还没有统一的系统设计协议，回答以下问题：何时需要类化、共性与变化点如何识别、领域 owner 与生命周期如何划分、采用哪种设计模式、消费者如何迁移，以及怎样证明设计在正式运行中确实成立。

因此，“类化完成”目前可能分别指抽出 helper、建立基类、引入 Runtime、迁移一个消费者或仅减少重复代码。这些口径不能互相替代，也不能证明：

- 公共职责已由唯一 owner 持有；
- 差异没有被塞入万能基类或按场景分支；
- 正式消费者已迁移，测试场景不是唯一集成者；
- 旧路径无法回流；
- 新增一个关卡、宠物或同类实体时确实只需声明差异；
- 数据、运行时状态、视图、资源和持久化边界没有重新耦合。

这是跨系统持续复发的架构缺口，不等同于 PG-013 的关卡专项，也不等同于本次宠物 AI 的单个功能缺失。

## 2. 证据

- PG-013 的关卡类化经历多轮用户反证：只抽关卡外壳仍遗留实体 Runtime，按关整理资源又错误地把怪物领域绑定到关卡。说明“抽出了公共类”不足以证明系统边界正确。
- 宠物领域已有 `PetSystem.ts` 中的大量规则函数、技能优先级和测试，但正式五关主要消费 roster、跟随身体与 HUD；目标选择、追击、普攻/技能调度、受击、死亡、奖励与写回尚未由同一个正式宠物战斗 Runtime 统一编排。
- `PetRuntimeSystem.ts` 当前只覆盖 idle/follow/warp。原版 `BasePet.myIntelligence()` 已有敌人搜索、距离判断、技能优先级、普攻和追击链，表明本次缺口不是“没有逆向”，而是逆向事实没有进入正式系统 owner。
- `PetSystem.ts` 已进入结构检查的大文件 warning 区间。继续向单文件增加物种与技能分支，会放大公共生命周期、物种策略和场景接线混杂的问题。
- 现有 `src-boundaries.md` 能约束若干已知目录和 owner，但没有要求架构类任务交付“共性/变化矩阵、消费者迁移矩阵、依赖方向、负向门禁和新消费者证明”。

## 3. 解决方案

本轮只登记问题，不创建执行队列项，也不提前冻结具体实现。后续对话应评审是否新增 `docs/workflow/system-design-protocol.md`，至少规定：

1. **设计输入**：可观察目标、非目标、原版事实/现代选择/未知、当前消费者与失败样本。
2. **边界建模**：领域 owner、持久状态、单局 Runtime、视图、资源、输入输出事件和销毁责任。
3. **共性与变化矩阵**：列出所有已知实体/场景的共同骨架、可替换策略、特例及禁止合并项。
4. **模式选择理由**：基类、模板方法、策略、状态机、组合、注册表或工厂只能用于解决已证明的变化轴；模式名称本身不是完成证据。
5. **消费者迁移合同**：列明存量消费者、迁移批次、兼容层删除条件和禁止继续使用的旧路径。
6. **验证合同**：静态 owner/依赖门禁、确定性单元测试、正式 Runtime 旅程、负向/变异测试和新增同类消费者样本。
7. **有界落地**：先冻结设计，再以一个纵向切片实现公共骨架和代表性差异，不一次性重构全部系统。

宠物系统的候选设计应把 `PetState`（持久事实）、`PetCombatRuntime`（单局可变状态）、公共战斗生命周期与物种/技能策略分开；可考虑“模板方法 + 策略 + 状态机/事件输出”的组合，但必须经后续设计评审裁决，不能在本问题登记时写成既定事实。

## 4. 测试方案

- 用 PG-013 的关卡类化过程和宠物类化方案作为首批反向样本，检查协议是否能提前暴露已发生的边界错误。
- 对未来系统设计任务校验是否存在：owner 图、共性/变化矩阵、消费者矩阵、迁移/回滚边界、测试与关闭合同。
- 静态检查正式消费者是否绕过共享 owner、复制帧循环或直接持有其他领域内部状态。
- 确定性测试公共模板与每个策略的输入输出；用负向样例证明错误 owner、未迁移消费者或旧路径回填会失败。
- 至少运行一条正式入口纵向旅程，不允许用 TestScene、单元测试或类名存在代替正式集成证明。
- 在系统完成后新增或迁移一个同类实体/关卡作为扩展性样本，核对是否只声明差异而无需复制公共生命周期。

## 5. 测试结果

当前只完成问题登记。系统设计协议、校验器、宠物设计和消费者迁移均未执行，因此不能把本问题标为“治理中”或“已解决”。

## 6. 关闭标准

- 系统设计协议落地，并明确设计输入、边界、变化轴、模式选择、迁移和验证的最低交付物。
- 至少以关卡类化复盘和宠物系统设计两个真实样本证明协议可发现边界缺口，而不是只增加文档字段。
- 架构/类化任务具有自动或可执行的 owner、消费者、旧路径和正式旅程门禁。
- 至少一个系统完成存量消费者迁移，并以新增同类消费者证明公共骨架可复用、差异无需回填到基类。
- 用户或 reviewer 的反例不会再出现“有基类/Runtime/测试，所以系统已完成”的自证式结论。

以下不算关闭：

- 只写设计模式教程或 UML，没有绑定项目 owner、消费者与迁移。
- 只拆大文件、改类名或引入接口，没有迁移正式入口。
- 只做单元测试，没有旧路径负向门禁和正式运行样本。
- 只为宠物或关卡写一次性方案，没有形成可复用协议并经过第二个系统验证。

## 7. 适用触发与反馈记录

触发条件：

- 用户提出“类化、系统设计、基类、公共 Runtime、统一框架、设计模式、共性接入”。
- 新增或重构跨两个以上消费者的系统、实体族、关卡族、Registry、Factory、Strategy 或生命周期 owner。
- 大类拆分、逐场景 bridge 复制、测试场景拥有正式功能、数据/Runtime/view/resource/save 边界变化。
- 评审以“已有抽象、测试通过、代码减少”为完成理由，但没有消费者迁移或运行验证。

效果检查：

- 检查设计产物是否同时给出 owner、生命周期、共性/变化矩阵、消费者迁移矩阵和禁止旧路径，而不是只有类图或模式名称。
- 搜索正式消费者是否仍复制帧循环、直接持有其他领域内部状态，或只在 TestScene 接入公共能力。
- 核对静态边界、确定性测试、正式入口旅程、负向门禁和新增同类消费者样本是否共同成立。
- 用户或 reviewer 提出新反例时，检查问题状态、设计方案和关闭口径是否在同次收尾中降级或修订。
