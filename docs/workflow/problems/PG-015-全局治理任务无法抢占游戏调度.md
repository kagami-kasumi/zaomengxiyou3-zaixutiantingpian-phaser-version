# PG-015 全局治理任务无法抢占游戏调度

状态：已关闭待归档（真实抢占通过，待空队列回退样本）。

来源：2026-08-01 用户要求把 PG-014 治理放到任务列表最前；首次只增加问题索引和看板说明，没有改变 `/goal` 的结构化 Ready 选择。随后用户执行 `/goal`，Agent 仍按游戏唯一 Ready 进入 Role2 逆向，证明现有任务系统缺少跨游戏/治理范围的统一调度层。

## 1. 问题定义

现有 `/goal` 只认识 Active 游戏功能线和 `task-board.md` 的唯一 Ready task。脚手架治理可以被登记为活跃 PG，也可以写在游戏看板顶部，但只要它没有进入结构化调度状态，就无法抢占游戏 Ready task。

这是任务系统边界缺失，而不是 PG-014 读取路由方案本身复发：

- Markdown 排列和说明文字不是可执行状态。
- PG 活跃索引负责问题扫描，不负责 `/goal` 调度。
- 游戏 `task-board.md` 被明确禁止承载 `TASK-DOCS-*`，无法合法表达脚手架工作。
- 校验器只验证游戏推荐、Ready task 与 Active 功能线一致，没有验证治理优先级。
- 游戏 task 完成时会重写当前推荐区域，临时前置文字容易消失。

如果不治理，任何需要暂停游戏工作的全局治理都只能依赖用户反复提醒；文档可以宣称“优先”，实际 `/goal` 仍会继续游戏队列。

## 2. 证据

- `AGENTS.md` 和 `agent-protocol.md` 均把 `/goal` 定义为执行游戏唯一 Ready task，没有治理队列检查。
- `TASK_OUTLINE.md` 明确写“实际调度以 `feature-lines.md` 和 `task-board.md` 为准”。
- `tools/validate-workflow.mjs` 的 `checkRecommendations` 与 `featureLineInvariantErrors` 只解析 `TASK-*` 行和游戏推荐项。
- PG-014 首次前置时没有改变游戏 Ready 状态；后续 `/goal` 实际执行并归档 `TASK-SETTINGS-069B`，而不是先执行前置治理。
- PG-014 随后完成了读取路由整改并归档，说明原问题已解决；本次失败的根因是跨范围调度模型缺失，应使用新 PG，而不是篡改 PG-014 的关闭事实。

## 3. 解决方案

1. 新增 `docs/tasks/execution-queue.md` 作为 `/goal` 第一调度入口，只记录会抢占游戏工作的活跃治理执行项，不复制游戏 task 状态。
2. 治理执行项直接引用活跃 `PG-*` 合同，允许 `Ready`、`Blocked`、`Planned`；最多一个 `Ready` 或 `Blocked`，按数字优先级升序。
3. `/goal` 先消费治理队列：治理 Ready/Blocked 存在时不读取或执行游戏 task；队列无可执行治理项时才回退到 Active 功能线和游戏唯一 Ready。
4. 游戏 `task-board.md` 继续只承载游戏 task，避免伪造功能线和机制/切片引用；统一队列负责跨范围先后顺序。
5. 治理项完成后从执行队列移除，完成事实回写 PG 与治理日志；同一次 `/goal` 到此停止，下一次才回退游戏 task。
6. 用户明确要求绕过或重排时，先持久化更新队列与 PG 状态，禁止只凭临时聊天跳过。
7. 扩展 `tools/validate-workflow.mjs`：校验队列文件、优先级、状态、PG 存在/活跃性、唯一可执行治理项和治理优先于游戏的正负样例。
8. 保留 `TASK-SLICE-158B` 的游戏 Ready 状态，在队列中放置 PG-015 验收项；下一次真实 `/goal` 必须选择 PG-015，验收后移除队列项并恢复游戏回退。

明确不做：

- 不把脚手架任务伪装成 `TASK-ARCH-*`、`TASK-DOCS-*` 或加入游戏任务表格。
- 不暂停或关闭当前游戏功能线，不修改其完成合同。
- 不允许多个治理 Ready 并行，也不在同一次 `/goal` 完成治理后继续游戏 task。
- 不依赖 Markdown 物理排列、自然语言“优先”或 Agent 自觉作为调度机制。

## 4. 测试方案

- `node --check tools/validate-workflow.mjs`。
- `npm run check:workflow`，确认执行队列、PG 索引、游戏 Ready 和 Active 功能线同时合法。
- 正向样例：一个治理 Ready 与一个游戏 Ready 共存时，当前全局执行项必须是治理 PG。
- 负向样例：两个治理 Ready、Ready 与 Blocked 并存、重复/非连续优先级、归档 PG 入队、缺失 PG 入队、非法状态均必须失败。
- 文档门禁：AGENTS、Claude、战略导航、根/工作流 README、文档地图和执行协议都必须声明先读 `execution-queue.md`。
- 真实验收：下一次 `/goal` 应只执行 PG-015 验收并移出队列，不进入 `TASK-SLICE-158B`；再下一次 `/goal` 才回退游戏 Ready。

- Agent/Claude、战略导航、根/工作流 README、文档地图、游戏看板和执行协议均已切换为先读 `execution-queue.md`、治理项完成即停止、队列空时才回退游戏 Ready。
- `node --check tools/validate-workflow.mjs`、`npm run check:workflow` 已通过；校验器报告 `current execution: PG-015 (governance)`，同时保留 `current recommendations: TASK-SLICE-158B`。
- 自动正向样例证明治理 Ready 抢占游戏 Ready，空队列样例证明可靠回退游戏推荐；七个负向样例覆盖双 Ready、Ready+Blocked、重复/非连续优先级、归档/缺失 PG 和非法状态。
- 仅保留既有 `PlayerSlot` 禁止别名 warning，与本次任务系统改造无关。
- 2026-08-01 的下一次真实 `/goal` 首先读取 `execution-queue.md`，在游戏 `TASK-SLICE-158B` 仍为 Ready 的同时只执行 PG-015 验收；本次未读取功能线、游戏看板、task 定义或 Role2/Role3 实现资料，也未修改 `src`。
- PG-015 已按合同从执行队列移除；当前队列为空，`npm run check:workflow` 应报告游戏 `TASK-SLICE-158B` 为下一全局执行项。尚待后续一次真实 `/goal` 证明空队列运行时回退，因此先进入“已关闭待归档”，不提前归档。

## 6. 关闭标准

- `/goal` 的所有入口文件都先路由 `execution-queue.md`，不存在继续直达游戏 Ready 的冲突文案。
- 自动校验能拒绝多治理 Ready/Blocked、无效优先级、缺失或归档 PG 和非法状态。
- 治理 Ready 与游戏 Ready 共存时，校验器报告治理 PG 为当前全局执行项。
- 一次真实 `/goal` 只执行 PG-015 验收并移出队列，没有读取/实现 `TASK-SLICE-158B`。
- 后续一次 `/goal` 在治理队列为空时能正常回退游戏唯一 Ready。

只有增加说明文字、只改游戏看板排列、只增加队列文件但不改 `/goal` 协议，或只有静态样例而没有真实抢占样本，都只能算部分缓解。

## 7. 适用触发与反馈记录

触发条件：

- 修改 `/goal`、`execution-queue.md`、游戏 Ready/推荐语义或功能线调度规则。
- 新增、完成、阻塞、绕过或重排治理执行项。
- 治理 Ready 存在时 `/goal` 仍执行游戏 task。
- 游戏 task 完成后覆盖、删除或绕过治理队列。
- 用户再次反馈“已前置但实际执行了别的任务”。

效果检查：

- 存量检查：所有入口和校验器是否使用同一治理优先调度语义。
- 增量检查：治理项生命周期是否能抢占、停止并在移除后可靠回退游戏。
- 反向检查：是否污染游戏功能线、产生多个 Ready owner 或复制游戏 task 状态。
