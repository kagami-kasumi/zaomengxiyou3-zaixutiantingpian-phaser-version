# PG-009 启动资源加载边界缺失

状态：方案落地，效果观察中。

来源：2026-07-24 用户反馈冷刷新长时间不可见；`TASK-SLICE-151` 新增选角资源后，全局 Boot 预加载进一步放大首屏延迟。

## 1. 问题定义

当前 `BootScene` 同时承担启动壳层、全部正式关卡、怪物、HUD、功能 UI 和 QA 资源的加载 owner。任何新场景或新资源族只要继续追加到 Boot，都会增加所有玩家冷启动的请求、下载和图片/SVG 解码成本，即使本次流程根本不会访问这些内容。

这不是单张图片或一个常量导致的局部性能问题，而是资源声明、加载时机、场景生命周期和回归验证边界缺失：

- 启动、地图、功能 UI 和各关卡没有独立 bundle owner。
- 正式路由没有统一的“进入场景前确保资源就绪”合同。
- 新资源可以直接回填 Boot，没有自动门禁阻止首屏成本持续增长。
- 当前进度条只能反馈等待，不能消除不必要的全量加载。

不治理会导致每增加一个关卡、怪物或原生 UI 都继续恶化启动体验，并迫使后续任务重复实现临时延迟加载。

## 2. 证据

- `src/scenes/BootScene.ts` 在同一个 `preload()` 中遍历 `role1NormalAttackAssets`、`craftingAssets`、`fullFeatureUiAssets`、`skillNativeUiAssets`、`combatHudAssets`、`heavenMapAssets`、Stage 1-1/1-2/1-3、Stage 2-1、怪物 atlas/攻击帧和 Stage 2-2 QA 资源。
- `src/assets/AssetManifest.ts` 已按资源族导出定义，但没有把资源族映射为具有加载状态、依赖和路由 owner 的运行时 bundle。
- `TASK-SLICE-151` 新增 25 条选人数/选角色原生资源后，刷新阶段长时间只显示空画布；把该资源族移出 Boot 只能缓解新增回归，既有全局加载仍然存在。
- 2026-07-24 本机 preview 构建主 JavaScript 约 2.4 MB；冷刷新等待主要还包含大量与首屏无关的图像/SVG 请求和解码。
- 当前专项测试验证资源存在和场景合同，但没有断言“存档首屏前不得请求关卡/功能 UI bundle”，也没有新资源回填 Boot 的负向门禁。

## 3. 解决方案

由 `GOAL-033` / `TASK-ARCH-012` 建立场景级资源加载边界：

1. 定义稳定 bundle 目录，至少覆盖 `shell`、`heaven-map`、`feature-ui`、`stage-11`、`stage-12`、`stage-13`、`stage-21`、`stage-22`。
2. Boot 正式路径只加载可交互启动/存档壳层；DEV/QA 直达路径只额外确保目标 QA bundle。
3. 建立无业务规则的 bundle loader/coordinator，提供幂等 `ensure`、并发去重、已加载查询、失败反馈与安全重试。
4. 地图、功能页和正式关卡通过共享入口在 scene 启动前确保目标 bundle 就绪；返回再进不得重复注册或重复下载。
5. 为 bundle 覆盖和 Boot 边界增加自动门禁；新增场景资源必须归属 bundle，禁止直接扩大全局 Boot。
6. 记录同一验收环境的变更前后首屏时间、首屏请求资源族和进入代表场景的首次/再次加载行为。

明确不做：

- 不更换 Phaser、TypeScript、Vite 或渲染技术栈。
- 本治理不批量转码 WebP/KTX2、不重导 SWF、不重做 atlas；格式压缩若仍有必要，依据测量另拆任务。
- 首轮不实现激进纹理卸载或内存淘汰；先闭合加载时机与唯一 owner，避免把内存生命周期混入同一 Goal。

## 4. 测试方案

- 静态门禁：Boot 正式路径不得引用 Stage/Monster/完整功能 UI 资源族；所有 ready 运行资源必须归属一个可追踪 bundle。
- 纯逻辑测试：覆盖 bundle 首次加载、并发 `ensure` 去重、已加载幂等、单文件失败、重试和依赖顺序。
- 路由测试：覆盖启动存档、地图、功能 UI、Stage 1-1/1-2/1-3、Stage 2-1/2-2 和 DEV/QA 直达。
- 构建与回归：运行相关专项、`npm run test:systems`、`npm run build`、`npm run check:workflow` 和 `git diff --check`。
- 浏览器验收：940×590 冷刷新立即出现原始启动/存档壳层；首次进地图/功能页/代表关卡有明确加载反馈，返回再进不重复加载，console 无 warning/error。
- 性能记录：在同一 preview 环境记录三次冷刷新中位数；首个可交互壳层目标不超过 1.5 秒且相对治理前至少降低 70%。若验收机器无法满足，问题不得标记关闭，必须记录剩余最大资源族。

## 5. 测试结果

- `TASK-ARCH-012` 已建立 `shell/save-party/heaven-map/feature-ui/combat-common/stage-*` 唯一 owner、依赖与路由映射；Boot 只排队 shell。
- `AssetBundleCoordinator` / `SceneAssetBundleBridge` 已覆盖幂等 ensure、并发去重、已加载查询、失败/重试、同 scene 串行和 shutdown 拒绝。
- `asset-bundle-tests.ts` 的重复 owner、无 owner、Boot 非 shell 回填和路由负向样例全部通过；`npm run test:systems`、build、workflow 与 diff check 通过。
- 同一 940×590 preview 首屏从 250 个资源/248 张图片降为 5 个资源/3 张图片；三次冷刷新为 1243/788/646ms，中位数 788ms。
- 地图首次进入只新增 6 张图，返回再进总资源数保持 11；Stage 1-1 不加载功能 UI/Stage 2-2，Stage 2-2 DEV 直达不加载地图/功能 UI/Stage 1-1；console warning/error 为 0。

## 6. 关闭标准

- Boot 正式路径只加载 `shell` 及其最小依赖；关卡、怪物、地图和完整功能 UI 不在首屏前请求或解码。
- 所有正式场景资源都有唯一 bundle owner；首次进入、并发进入和返回再进入合同由自动测试覆盖。
- DEV/QA 直达仍可用，且不会迫使正式启动加载全部 QA 资源。
- 新增资源回填全局 Boot 的负向样例会被自动校验拒绝。
- 冷刷新性能达到本问题测试方案中的相对与绝对目标，并留下请求资源族、三次测量和 940×590 运行证据。
- 相关专项、全系统、build、workflow、diff check 与 console 检查全部通过。

仅增加进度条、只延迟一个资源族或减少个别图片不能算关闭。

`TASK-ARCH-012` 已满足上述存量关闭标准；本问题转为效果观察。后续新增关卡、怪物、HUD、菜单或资源族仍须由自动门禁和本节触发条件持续采样，若 Boot 回填、重复请求、缺纹理或失败卡死复发则退回治理。

- 冷刷新、首次进场、返回再进出现明显等待、重复请求、缺纹理或 loader 卡死。
- 任务声称优化首屏、资源分包、按需加载、内存或加载失败恢复。

- 搜索 Boot 是否重新直接遍历非 `shell` 资源族。
- 核对新增 ready 资源是否具有唯一 bundle owner 和路由消费者。
