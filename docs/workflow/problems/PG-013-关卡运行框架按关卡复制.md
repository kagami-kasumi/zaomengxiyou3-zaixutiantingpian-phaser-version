# PG-013 关卡运行框架按关卡复制

状态：复盘中（V2A/V2B 已完成，V2C Ready）。

来源：2026-07-31 用户从 Stage 1-1 光门/黑框差异继续追问“关卡类化”，指出不应只抽取单个光门，而应治理所有关卡共同职责按关复制，以及关卡承载角色、怪物或视觉内部规则的边界漂移。

2026-08-02 用户再次明确指出人物动作、怪物运行不应由关卡承载。现状证明 V1 只统一了关卡外壳，未建立实体运行时 owner；按问题治理协议转入复盘。

## 1. 问题定义

现代实现已经抽出 `LevelLifecycle`、`LevelResultView`、角色移动、战斗、奖励和功能 HUD 等局部公共 owner，但仍没有完整、稳定的可玩关卡运行框架。Stage 1-2、1-3、2-1、2-2 分别复制 Scene 初始化/销毁、队伍恢复、镜头、玩家创建、World/GamePlay 接线、结果路由；Stage 1-1 则继续寄居在大型 `TestScene` 与多组 bridge 中。

同一关卡共同事实因此分散到 `Stage*Scene`、`Stage*WorldBridge`、`Stage*GameplayBridge`、`Stage*FlowSystem` 和资源 manifest。每新增一关仍需人工复制并重新接线基础设施，容易再次遗漏门视觉、失败、结果、保存、HUD 或销毁。反方向上，关卡也可能开始拥有英雄/怪物内部动画、AI、伤害和奖励规则，形成职责膨胀。

不治理会使后续关卡数量与重复 owner、回归路径和修复成本近似线性增长；局部抽一个 `TransferDoorView` 只能缓解一个症状，不能关闭问题。

## 2. 证据

- `Stage12Scene.ts`、`Stage13Scene.ts`、`Stage21Scene.ts`、`Stage22Scene.ts` 重复持有 party/playerCount/world/gameplay/playerViews/resultOverlay，并重复 init/create/update/shutdown 骨架。
- 四个 `Stage*WorldBridge` 分别创建 floor/background/foreground/transferDoor；四个 `Stage*GameplayBridge` 分别控制 `transferDoor.setVisible(flow.doorVisible)` 并把同义玩家输入适配到公共生命周期。
- Stage 1-1 的 `createTransferDoorView()` 直接借用 `Stage13AssetKeys.transferDoor` 并按 character 45 的 bounds 手动缩放；资源 provenance、可复用视觉定义和关卡运行 owner 混在一起。
- 五个 `Stage*FlowModel` 已继承 `LevelLifecycle`，证明通关终态可共享；但 `PG-012` 的黑框复发证明只抽局部生命周期不足以覆盖完整关卡模板。
- 原版 `PhysicsWorld.addSubObj()` 统一登记 `isTransferDoor`，`BaseHero.checkTransferDoor()` 统一检测所有关卡门；各关 SWF 嵌入不同 character 是资源打包事实，不等于现代行为 owner 必须按关复制。
- 原版仍有全局 `gc`、逐角色按键复制、`StageListenerXX` 和时间轴强耦合等债；现代架构只能保留可观察行为，不能把这些结构当模板。
- V1 落地后，`Stage12/13/21/22GameplayBridge` 仍各自声明 `PlayerRuntime` 和 `EnemyRuntime/MonsterRuntime`，各自创建玩家 combat model 与怪物 Map，并各自调用 `updateStage1CombatPlayer`、`updateStage1Enemy`、`resolveStage1EnemyAttack`、`resolveStage1HeroAttack`、物理、奖励和视觉同步。四关共有四套实体帧循环。
- 2026-08-02 “下一关后攻击对象消失”正是该边界的运行反证：普通攻击视觉此前只存在于 TestScene；局部修复虽然抽出了 `HeroNormalAttackVisualBridge`，但仍要在四个关卡 bridge 分别创建和调用，说明实体生命周期 owner 仍未闭合。
- `src-boundaries.md` 已声明 `MonsterRuntimeRegistry` 应保存单局可变怪物状态，但 `src/` 中没有该实现；当前四个关卡 Map 才是事实上的运行时 owner。`PlayableLevelRuntime` 只调用关卡提供的 `createEncounter`，没有持有英雄/怪物帧调度。

## 3. 解决方案

1. 先审计五关全部共同职责和真正差异，冻结消费者矩阵、owner、迁移顺序与禁止边界。
2. 建立组合式 `PlayableLevelRuntime` / `LevelDefinition` 合同，公共运行框架统一队伍、镜头、玩家、HUD、移动/战斗调度、失败、出口、结果、保存、路由和销毁。
3. 关卡定义只声明世界边界、出生点、出口/解锁/路由和所需 adapter；`LevelEncounter` 只编排停点、波次、Boss 与机关。
4. 建立共享 `TransferDoorView` 行为/状态合同；透明资源、动画集合和原始 Symbol 差异由可替换 `TransferDoorVisualDefinition` 表达，关卡只引用 visual id 与位置。
5. 英雄/怪物的动画、AI、物理、伤害、奖励继续属于各自定义和系统；关卡只能引用类型/视觉 id，不能拥有其内部算法。
6. 使用组合、配置和窄 adapter，不建立同时承载世界、怪物、UI、资源、存档和路由的万能 `BaseLevel`。
7. 先迁移两关试点，再按 Stage 2 与 Stage 1-1/TestScene 分批迁移；保持兼容 facade，禁止一次性重写五关。
8. 首个后续新关卡必须直接消费公共框架；否则本问题只能进入效果观察，不能关闭。

### 方案 V2：实体运行时独立于关卡

V1 的 Scene/结果/路由/门框架继续保留，但废弃“GameplayBridge 作为窄 adapter 已足够”的判断。V2 分批建立两个关卡无关 owner：

1. `HeroPartyRuntime` 统一创建并持有玩家移动、战斗、普攻、技能、角色本体和攻击对象视觉生命周期。关卡每帧只提供平台、移动边界和特殊环境快照，不创建角色 combat model，不调用角色动作/攻击更新。
2. `MonsterRuntimeRegistry` 统一登记稳定怪物 id、可变战斗状态、AI/物理、攻击结算、死亡与奖励上报；关卡无关视图 adapter 按稳定 id 维护 Phaser view 映射。关卡遭遇只发出带 monster definition/profile id 的 spawn 命令，并消费 `spawned/defeated/cleared` 事件；不持有怪物 Map，不调用怪物内部更新。
3. `LevelEncounter` 只保留地形、停点、波次、Boss 组合、机关和通关门禁；`LevelWorldAdapter` 只保留 Phaser 世界/地形/机关显示适配。资源 bundle 属于入口加载策略，也不能成为实体行为 owner。
4. 不建立万能 `BaseLevel` 或完整 ECS；优先组合既有 `LevelHeroMovementRuntime`、`Stage1CombatSystem`、各角色/怪物 visual bridge、`MonsterPhysicsSystem` 和 `Stage1RewardBridge`，先收敛生命周期和调度 owner。
5. 迁移分批执行：V2A 冻结消费者矩阵、接口和静态门禁；V2B 只建立 `HeroPartyRuntime` 并迁移 Stage 1-2；试点完成后才按证据生成其余 Hero 消费者批次。Monster 另起单-owner试点，以 Stage 1-2 建立 `MonsterRuntimeRegistry`，再生成其余消费者批次，最后收缩 Stage 1-1/TestScene 兼容面。任一批最多处理一个明确 owner，不一次性创建 Hero 与 Monster runtime 或重写五关。

V2A 明确不修改数值、动作帧、怪物 AI、关卡波次、地形或视觉资源；它只决定谁拥有实体运行时，并把后续迁移拆成可独立验收的工作包。

V2A 方案选择：继续加厚 `PlayableLevelRuntime` / GameplayBridge 可以减少文件数，但会把英雄、怪物、世界与关卡内容重新集中成万能关卡 owner，因此废弃；选择组合式实体 runtime，由 `PlayableLevelRuntime` 只调度环境快照、spawn 命令与实体事件。V1 的 Scene/门/结果/保存/路由成果全部保留。

V2A 已冻结以下交付合同：

- `HeroPartyRuntime` 按 `PlayerSlot` 唯一持有英雄移动、战斗、普攻、技能、本体和攻击对象视觉生命周期；关卡只提交 `InputState`、平台/边界/特殊环境与怪物目标快照。
- `MonsterRuntimeRegistry` 唯一持有稳定怪物 id 与单局可变状态；遭遇只提交 `MonsterSpawnCommand`，消费 `spawned/defeated/cleared` 事件。Registry 不持有 Phaser 对象，view mapping 由关卡无关实体视图 adapter 按稳定 id 投影。
- 五关消费者矩阵和单-owner迁移顺序位于 `docs/architecture/playable-level-runtime.md`；V2B 只处理 Hero owner + Stage 1-2，不触碰怪物 Map/AI/奖励、Stage 1-2 波次/双 Boss/`fbEnter` 或视觉资源。
- `check:level-architecture` 冻结四个 GameplayBridge、`Stage22DevGameplayBridge` 与 TestScene 的实体 owner token 预算；新关卡/adapter 回填同义 runtime、实体 Map 或直接 update/resolve 会失败，遗留预算只能随迁移缩减。
- `LINE-MONSTER-ARCH / TASK-ARCH-010A` 后续只负责怪物定义目录、Brain/Targeting 与无关卡命名规则；`TASK-ARCH-010B` 改为把这些合同接入 PG-013 已建立的 Registry，不再创建第二个注册表。

V2B 试点已建立 `HeroPartyRuntimeSystem` 与 `HeroPartyRuntimeBridge`：纯系统唯一持有活动英雄的移动、战斗、普攻、技能状态和共享战斗命中 registry；Phaser bridge 统一投影角色本体、普攻对象、技能更新事件、HUD/奖励兼容快照与幂等销毁。Stage 1-2 已删除 `PlayerRuntime`、私有 movement runtime、玩家 update/resolve 和普攻视觉生命周期，只提交输入、平台/边界快照和怪物目标，并保留未迁移的怪物 Map/AI/物理/奖励/波次。

试点保留了旧帧顺序：英雄移动/动作 → 停点与 spawn → 怪物 AI/攻击 → 英雄攻击结算 → 死亡/奖励 → 失败/门/镜头。由于 Monster owner 尚未迁移，V2B 暂以 `resolveEnemyAttack`、`resolveAttacks` 和 `rewardPlayers` 作为显式兼容 facade；后续 Monster runtime 接入时删除这些可变模型接缝，不将其外推为最终关卡合同。

依据 V2B 的 1 个共享 owner + 1 个正式关卡消费者规模，剩余 Hero 消费者固定拆为四批：V2C Stage 1-3；V2D Stage 2-1；V2E Stage 2-2 正式与 DEV（必须同批避免双 owner）；V2F Stage 1-1/TestScene 兼容面。每批只迁移 Hero owner 并收缩对应静态预算，不触碰怪物 owner；四批完成后才进入独立 Monster Stage 1-2 试点。

## 6. 关闭标准

- 五个现有关卡全部消费唯一公共可玩关卡运行框架，关卡差异通过定义、遭遇和窄 adapter 表达。
- 公共队伍、玩家、镜头、HUD、移动/战斗调度、失败、出口、结果、保存、路由和销毁没有逐关同义 owner。
- 关卡不拥有英雄/怪物动画、AI、伤害、物理或奖励内部规则。
- 传送门共享行为/状态 owner；不同原始 Symbol/动画只作为可替换视觉定义，不按关复制逻辑。
- 五关确定性测试、全系统、构建与规定运行旅程无回归，静态门禁可阻止新增复制。
- 至少一个后续新关卡直接消费公共框架；仅迁移存量五关时进入效果观察，不提前关闭。
- V2 追加关闭条件：正式关卡不得声明玩家/怪物 runtime 类型或实体 Map，不得直接调用角色/怪物内部 update/resolve；只能提交环境快照、spawn 命令并消费实体事件。
- V2 追加关闭条件：Hero/Monster runtime 的纯系统测试、Stage 1-2 试点、其余四关迁移、TestScene 兼容和静态防回填门禁全部通过；只抽一个视觉 helper 或减少重复行数不算关闭。
