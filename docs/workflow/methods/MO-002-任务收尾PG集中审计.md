# MO-002 任务收尾 PG 集中审计

状态：试验中。

提出者/来源：用户提出用 MO 机制完成 PG 校验与归档，并将重复校验记录从单个 PG 文件抽离；2026-08-06 脚手架讨论。

负责人：每次适用工作的主 agent；协议级汇总由 workflow steward 负责。

最迟复核点：取得 3 个真实收尾样本后，且不得晚于 2026-09-15。

## 1. 方法与假设

方法：每次代码、架构、游戏 task 或工作流变更收尾时，通过 `problem-audit.md` 和 `npm run audit:problems` 统一生成活跃 PG 审计包；正常结果集中记录一次，允许同一份证据同时作为 MO 方法样本和 PG 关闭样本。满足全部 PG 关闭合同时，在同次收尾直接归档，不再人为延迟。

假设：集中执行与单点记录能够降低逐个 PG 重复扫描、重复日志和长期“观察中”滞留，同时不增加漏检、误归档或失去问题历史语境的风险。

本方法不把“MO 方法成功”改写为“PG 已关闭”。单个 PG 仍拥有问题特有的关闭标准、反证、方案版本和重开信号；集中审计只复用执行与证据。

## 2. 基线与指标

基线：任务收尾由执行者逐个打开活跃 PG，在多个问题文件重复写入相似的“扫描通过”行；PG-004 已积累大量跨任务重复记录，但仍长期处于运行观察状态。

主指标：

- 每个任务为 PG 反馈新增的日志行数与重复证据次数；
- 从当前 diff 到确定命中 PG 所需的读取/搜索次数；
- 审计后满足关闭标准却未归档的 PG 数量；
- 集中审计证据被 PG 关闭合同直接采用的数量。

护栏指标：

- 漏掉明确触发的活跃 PG 数必须为 0；
- 错误归档或遗漏反证数必须为 0；
- 归档 PG 的关闭标准、持久防线和重开信号缺失数必须为 0；
- 正常通过样本集中记录后，PG 的方案版本与历史反证仍必须可独立追溯。

## 3. 试验设计

- 取得至少 3 个真实样本，至少覆盖两类场景：游戏代码/架构变更、任务/工作流维护、逆向或 UI 验收。
- 每次样本先运行 `npm run audit:problems`，再由主 agent 语义判断实际命中项；工具输出不能代替语义判断。
- 每个样本只在 `problem-audit.md` 集中写一行；只有状态变化、反证、换案或归档时才同步更新单个 PG。
- 样本达到某个 PG 的最后一项关闭条件时，必须当场完成归档评估；满足全部条件则直接归档，否则记录精确缺口。
- 对照最近同类任务的逐 PG 反馈行数、读取次数和归档滞留情况；无法可靠计时时使用日志行数与重复证据数。

停止条件：出现一次错误归档；出现一次明确命中 PG 被集中审计漏掉且直到交接后才发现；连续两个样本的记录成本不降反升且没有提高归档及时性。

## 4. 采纳标准

- **采纳**：至少 3 个样本覆盖两类场景；重复反馈行数明显下降；至少一份集中证据被 PG 关闭合同采用或促成精确缺口判断；所有护栏指标为 0。
- **修订**：集中记录有收益，但候选生成、语义触发、归档评估或回写边界仍需调整。
- **停止**：命中停止条件，或 3 个样本后没有减少重复记录与归档滞留。

单个成功样本不能证明该方法应长期采纳；但如果同一份证据已经满足某个 PG 的全部剩余关闭条件，它可以直接促成该 PG 归档。
