# 具体系统设计与设计模式机制

状态：已生效。

本文只负责为一个具体系统（例如关卡、宠物、怪物、技能、背包或存档系统）确定当前设计模式和代码规约。它由用户明确要求时执行一次；Agent 不得因为发现重复代码、大文件、多个消费者或潜在设计模式而自行触发。

设计阶段只产出一套方案，不并行设计或实现多套方案作比较，也不生成“无设计模式版本”。类化、基类和模板方法只是设计模式的一种实现方式。

设计完成后的逐批代码检查不属于本文，统一由 `system-design-acceptance-protocol.md` 反复执行，直到整个系统验收完成。

## 1. LLM 读取与设计步骤

用户明确触发后，LLM 按以下顺序工作：

1. **锁定具体系统**：明确本次设计的是关卡系统、宠物系统或其他单一系统，以及要简化的开发动作。
2. **读取现状**：读取本文、`src-boundaries.md`、该系统已有设计文档，再窄读相关实现和全部正式消费者；依赖原版行为时补读对应逆向证据。
3. **定位重复与变化**：列出真实存在的重复流程、分支、数据、接线和容易漏改的位置；只用于确定方案，不生成对照实现。
4. **选择一种方案**：直接选择最适合当前结构的一种主模式或一种组合方案，并说明它解决哪类重复、公共流程放在哪里、差异从哪里注入。
5. **冻结模式规约**：把模式参与者、源码映射、调用顺序、扩展点、禁止路径、消费者和验收要求写入 `docs/architecture/system-designs/<system>.md`。
6. **生成硬门禁**：在 `tools/check-system-design.mjs` 为每个迁移批次建立可执行 gate，明确必需类/方法、依赖方向、禁止入口和专用行为合同测试；门禁必须以进程退出码给出成功或失败，不能只输出建议。验收文档中的“门禁覆盖映射”只帮助 LLM 把规约翻译成机器断言，不是机器门禁之外的人工验收层。
7. **核定现有完成度**：先按实际代码判断公共流程、差异入口、正式消费者和旧路径已经完成多少；旧系统不能因为文件多或历史久就假定已经类化完成。运行全量 gate 留下当前失败基线，不用人工文字冒充通过。
8. **建立实施交接**：把具体设计链接到需要实施的当前及后续 task，按现状把验收状态设为 `未开始` 或 `实施中`，并列出迁移批次、对应 gate、最终完成条件和退出条件。不得为了接入设计而改写当前无关的 Ready task。

设计只输出一个结论。不能为了形式完整列出多个模式再逐一比较，也不能实现多个版本比较代码量或开发耗时。

## 2. 设计模式规约

每份具体系统设计必须把抽象模式翻译成可以检查的项目规则：

1. **选定模式**：模式名称或组合方式，以及它要消除的具体重复。
2. **角色映射**：模式中的 Context、Strategy、State、Template、Factory、Registry、Command、Facade 等角色分别对应哪些文件、类、函数或数据表。
3. **协作顺序**：正式调用从哪里进入，各角色按什么顺序交互，结果从哪里返回或发布。
4. **公共逻辑唯一位置**：哪些算法、生命周期或创建流程只能定义一次。
5. **允许扩展点**：新增关卡、宠物种类或行为时允许新增/修改哪些位置。
6. **禁止路径**：消费者不得直接实例化什么、不得绕过哪个入口、不得重新出现哪些 `switch`、复制流程或第二数据源。
7. **消费者全集**：列出所有正式消费者、测试消费者、当前接法、目标接法和迁移批次。
8. **验收合同**：每条规约在迁移期由哪个静态检查、合同测试或正式运行旅程证明，整个系统满足什么条件才算完成并退出验收。

常见模式应至少满足以下可检查约束：

| 选定模式 | 必须遵守的核心规约 | 典型违规 |
| --- | --- | --- |
| 数据驱动/Registry | 定义只有一个目录；消费者按稳定 id 查询 | scene 重新定义表或按类型写第二套 `switch` |
| Strategy | Context 持有公共流程；差异只经策略接口注入 | Context 同时判断具体类型，消费者复制算法 |
| State/状态机 | 状态、事件和转移由单一状态机裁决 | scene 直接改状态或用散落布尔值旁路转移 |
| Template Method/继承 | 基类固定公共步骤；子类只实现声明的钩子 | 基类按子类类型分支，子类重写完整公共流程 |
| Factory | 创建入口唯一；调用方不直接构造具体实现 | 正式消费者继续 `new` 具体类或复制初始化顺序 |
| Command/Event | 发起方只发命令/事件；执行与订阅生命周期明确 | 发起方同时直接写状态，事件监听不销毁 |
| Facade/Adapter | 正式消费者只依赖统一入口；旧接口只在适配层出现 | 消费者绕过 Facade 直接访问内部子系统 |
| Composition | 能力边界和组合顺序固定；公共协调逻辑有唯一 owner | 每个实体重新编排同一组能力调用 |

## 3. 人工重设计

具体系统设计文档只代表当前有效方案。人工可以根据效率、维护性、开发体验、可读性或项目方向直接要求重新设计，不需要先证明存在严重缺陷，也不需要走 PG、MO 或方案复盘流程。

收到人工重设计指令时：

- 停止继续扩展旧方案，重新读取当前系统实现和人工要求；
- 直接修改或替换当前设计，不在正文保留旧方案、候选比较或废弃版本；
- 按新方案重新冻结角色、入口、扩展点、消费者、禁止路径和验收合同；
- 将验收状态重置为 `未开始` 或按已迁移代码重新核定为 `实施中`；
- 旧方案历史由 Git 记录即可，除非人工明确要求另写决策历史。

## 4. 设计完成与交接

设计阶段完成只表示“规约已经确定”，不表示系统实现完成。设计交接必须同时留下：

- 一份当前具体系统设计文档；
- 选定模式及角色到源码的预期映射；
- 消费者全集和迁移批次；
- 禁止路径及其可执行检查；
- `npm run check:system-design -- <system> <gate>` 的批次门禁和 `all` 最终门禁；
- 至少一个由门禁实际执行的系统专用行为合同测试；
- 后续 task 对设计文档和 `system-design-acceptance-protocol.md` 的链接；
- 按现状核定的 `验收状态`、`验收退出：未退出`，以及系统级最终完成与退出条件。

后续每个关联实现或评审 task 均由验收机制更新进度，直到同一批次标记 `验收状态：已完成`、`验收退出：已退出`。退出后普通开发不再读取设计验收机制、不再执行设计模式专项扫描，也不再追加批次记录；设计机制本身不重复执行，除非用户明确要求重设计或重新开启验收。
