# PG 集中审计协议

状态：试验运行中，由 `MO-002` 观测。

本文承接代码、架构、游戏 task 和工作流变更的收尾 PG 扫描、集中样本记录与归档评估。它从单个 `PG-*` 文件中抽离重复执行流程，但不抽走问题特有的关闭合同。

## 职责边界

- `problem-governance.md` 维护 PG 状态机、活跃/归档索引和通用关闭门禁。
- 单个 `problems/PG-*.md` 保留问题定义、根因证据、方案版本、问题特有的触发条件、效果检查、关闭标准、反证和最终关闭摘要。
- 本文件统一维护“何时扫描、如何记录一次任务结果、何时发起归档评估”。正常通过样本只写一处，不再逐个复制到所有命中的 PG 文件。
- `MO-002` 观测集中审计方法是否降低重复记录、漏检和长期滞留；同一份证据可以同时成为 MO 方法样本和 PG 关闭样本。
- “MO 方法有效”和“某个 PG 已满足关闭合同”是两个独立判断。前者不能替代后者，但两者可以复用同一证据。

## 任务收尾审计

代码、架构、游戏 task 或工作流变更收尾时执行：

```bash
npm run audit:problems
```

命令读取当前 diff、活跃问题索引和每个活跃 PG 的触发/效果合同，生成窄审计包。执行者随后：

1. 根据当前 diff 和工作流事件做语义匹配，不以路径未命中自动判定不适用。
2. 只对实际命中的 PG 运行其关闭合同指定的搜索、测试、覆盖差异或评审。
3. 在下方集中审计表写一行，结论使用 `通过`、`复发`、`方案不充分` 或 `不适用`。
4. 正常通过且不改变 PG 状态时，不再向各 PG 的历史反馈表复制同一行；出现反证、换案、状态变化或最终归档时，才回写相应 PG。
5. 若当前工作命中 `MO-002` 的采样条件，同一行同时提供方法指标，并在达到样本量或停止条件时更新 MO 裁决。

归档问题不进入常规扫描，只在用户/reviewer 报告复发、持久门禁失败、新设计推翻旧决策或变更直接引用其 PG id 时定向重开。

## PG 归档评估

一次审计结论为 `通过` 后，立即评估命中 PG 是否同时满足：

1. 单个 PG 的关闭标准全部完成且没有未解释反证。
2. 存量清理与增量防复发均有可定位证据。
3. 已留下自动测试、静态门禁、唯一 owner 合同或可执行评审规则之一。
4. 关闭合同要求的样本类型和数量已经满足；同一份集中审计证据允许计入。
5. PG 已写明关闭摘要、持久防线、归档日期和精确重开信号。

五项全部满足时，应在同一次收尾中直接归档 PG：更新独立 PG 状态和归档信息、从活跃索引移入归档索引，并在集中审计行记录“可归档/已归档”。不额外保留人为等待期。任一项不满足时记录缺口，不得因为 MO 样本成功或单次测试通过提前归档。

`复发` 或 `方案不充分` 必须在同次收尾回写 PG，转入 `复盘中` 并建立方案新版本；集中日志不能代替问题文档中的反证和换案历史。
