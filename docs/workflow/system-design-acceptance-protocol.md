# 具体系统设计模式验收机制

状态：已生效。

本文负责验证实际生成的代码是否遵守某个具体系统已经冻结的设计模式规约。它与一次性的设计机制分离：设计通常只由用户触发一次，验收会在多个实现、迁移和评审批次中反复执行，直到整个系统完成并退出。

验收不是重新选择设计模式，也不比较多套方案或代码量。发现代码偏离时，默认修正实现；只有用户明确要求重新设计时，才返回 `system-design-protocol.md`。

## 1. 重复验收路由

具体设计建立后，实际承担迁移的当前及后续实现 task 必须链接 `docs/architecture/system-designs/<system>.md`。只要该文档同时满足 `验收状态` 不是 `已完成`、`验收退出` 不是 `已退出`，每个关联实现或评审 task 收尾都必须读取本文和该设计文档，执行本批验收。

Agent 不扫描全部 `system-designs/` 猜测适用性，只消费当前 task 明确链接的具体设计。一次验收只覆盖当前批次及其影响的既有消费者，但必须更新系统级剩余清单。

验收状态只有三种：

- `未开始`：设计规约已冻结，尚无实现批次通过。
- `实施中`：至少一批实现符合规约，但仍有消费者、旧路径或系统级证据未完成。
- `已完成`：所有角色、消费者、禁止路径、合同测试和正式运行证据全部满足，剩余清单为零。

另设验收退出状态：

- `未退出`：仍处于迁移与重复验收期。
- `已退出`：系统级验收已经完成；本机制不再适用于后续普通开发。

## 2. 硬性验证方式

验收采用“静态结构门禁 + 可执行行为合同 + 正式消费者回归”三层证据，统一由以下命令触发：

```bash
npm run check:system-design -- <level|pet|hero> <批次 gate>
```

- 静态结构门禁直接读取 `src`，检查必需类/方法、唯一 Factory/Registry、依赖方向、正式消费者入口、旧分支和兼容文件；任一不符即退出码 `1`。
- 行为合同测试由门禁调用 `tools/run-system-tests.mjs` 执行，必须用 spy/fixture 证明公共步骤顺序、差异钩子、调用次数、状态输出和幂等销毁；缺少测试文件也直接失败。
- 正式消费者回归由后续 gate 调用既有正式系统/旅程测试，证明结构不是只在 mock 或 TestScene 中存在。
- 参数或 gate 不存在时退出码 `2`；只有退出码 `0` 才能记录该批通过。文档勾选、人工判断、编译成功或普通测试通过都不能替代 gate 的 `0`。
- 每个迁移 task 必须声明本批 gate。系统最终完成必须运行 `npm run check:system-design -- <system> all`，全量退出码不是 `0` 时禁止标记完成或退出。
- 门禁不加入 `check:all` 或其他默认检查链；只在未退出设计明确链接的迁移 task 中调用，满足退出机制。

门禁检查的是可观察、可执行的项目规约，不声称从语言层面数学证明某种设计模式。静态结构与运行时行为必须同时满足，避免“类名存在但代码绕过”或“测试能跑但结构仍复制”两种假通过。

## 3. 每批验收步骤

1. **读取 gate 名称**：从具体设计和当前 task 确认本批唯一 gate，不重新做一次人工架构评审。
2. **运行本批硬门禁**：执行 `npm run check:system-design -- <system> <gate>`；静态结构、行为合同和正式消费者测试全部由该命令触发。
3. **按退出码裁决**：退出码非 `0` 时本批不通过，按机器输出修正代码；退出码为 `0` 时本批通过。不得另设人工覆盖结论。
4. **更新进度记录**：把机器输出、已通过 gate 和剩余 gate 写回设计文档；最终只有 `all` 为 `0` 才进入退出记录。

## 4. 门禁覆盖映射（只供 gate 作者使用）

本节不是独立验收层，也不是让人或 LLM 在每批完成后填写的检查表。它只供设计者/LLM 编写 `tools/check-system-design.mjs` 和系统专用测试时使用：把自然语言规约逐项翻译成机器断言。某一行没有落入 gate，就表示门禁定义不完整，必须先补门禁；不能在验收时用“实现阅读”补票。

| 设计语义 | 必须落入 gate 的机器断言 | 失败时由谁报告 |
| --- | --- | --- |
| 角色存在与职责 | 必需文件、类、继承、方法和禁止依赖的静态断言 | `check-system-design` 静态 gate |
| 依赖与入口 | 正式消费者 import/call 必须指向唯一入口，具体类只能由 Factory/Registry 创建 | `check-system-design` 静态 gate |
| 禁止路径 | 旧构造、旁路写状态、第二数据源、旧分支和兼容文件必须不存在 | `check-system-design` 负向 gate |
| 模式合同 | 公共步骤顺序、钩子调用、状态转移、策略选择、错误输入和幂等销毁必须有确定性断言 | gate 强制调用的系统专用行为测试 |
| 正式接入 | 正式 Runtime/1P/2P 消费者必须在运行测试中经过新入口 | gate 强制调用的正式系统/旅程测试 |
| 迁移遗漏 | `all` 必须组合全部批次 gate，并对消费者全集和旧路径作最终负向断言 | `check-system-design <system> all` |

## 5. 批次结论

每批只能给出以下结论之一：

- `本批通过，系统实施中`：本批范围全部符合，但系统仍有明确剩余项。
- `本批不通过`：实际代码偏离规约、测试失败、正式接入缺失或证据不足；列出必须修正的实现，不改设计规约。
- `系统验收完成并退出`：本批通过、`all` gate 退出码为 `0` 且系统级完成条件全部满足；同批执行退出动作。

不能因为本批代码编译、设计角色存在、单个消费者成功或测试数量很多，就宣布整个系统完成。

## 6. 系统级完成条件

代码规约只有一个技术完成判据：

```bash
npm run check:system-design -- <system> all
```

该命令返回 `0`，即表示角色、依赖、禁止路径、模式行为合同、正式消费者和迁移遗漏已由机器门禁全部证明；返回非 `0` 就是未完成，不再增加一层人工技术裁决。

同一批次还必须清空剩余清单，并同步 task、覆盖台账、稳定 architecture 边界和退出记录。这些只是进度与追溯 bookkeeping，不重新判断代码是否符合设计模式。

若任一项未满足，状态保持 `实施中`，由下一个关联 task 继续验收。

## 7. 验收退出

满足系统级完成条件的同一批次必须完成以下动作：

1. 将具体设计文档改为 `验收状态：已完成`、`验收退出：已退出`，写明退出日期、task 和最终证据。
2. 清空系统级剩余清单；当前未完成 task 若只因重复验收而链接该设计，应移除该验收链接。历史完成 task 的链接可保留为追溯记录。
3. 停止在后续普通实现、评审和收尾中读取本文或追加验收批次；不得扫描已退出设计，也不得因代码再次触及该系统而自动重开。
4. 停止设计模式专项静态扫描和专项符合性测试进入默认检查链；正常的类型、构建、行为和回归测试继续保留，但不再以“是否遵守该设计模式”为检查目标。
5. 只有用户明确要求重设计或重新开启验收时，才可将退出状态改回 `未退出`，并按当前代码重新核定 `未开始` 或 `实施中`。

退出表示验收机制结束，不要求删除设计文档或把已经稳定的代码重新改回去。

## 8. 验收记录

退出前每次验收都在具体系统设计文档的“验收批次记录”中追加一行，至少包含 task、范围、静态检查、合同测试、正式运行、结论和剩余项。退出批次写最后一行，此后停止追加。正常批次不写入 PG 审计；只有当前工作另行命中活跃 PG 时，才按 `problem-audit.md` 处理。
